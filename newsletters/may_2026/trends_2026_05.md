## エグゼクティブサマリー

今期のエージェント研究は、abstractレベルで読み込むと次の **4本の太い柱** に明確に収束する。

1. **Skill / Harness を一級市民として扱う設計学の成立**
   `A Comprehensive Survey on Agent Skills`（Zhou et al., [2605.07358](https://arxiv.org/abs/2605.07358)）が「ツール・メモリ・実行時コンテキストをタスク特化制約下で協調させる再利用可能な手続き的アーティファクト」としてSkillを定義し、表現・獲得・検索・進化の4フェーズで文献を整理した。これに呼応するように、`SkillScope`([2605.05868](https://arxiv.org/abs/2605.05868))が**過剰権限を88.56%削減**、`Ratchet`([2605.22148](https://arxiv.org/abs/2605.22148))が**ベースライン以下に劣化しないことを数学的に保証**、`SkillsVote`([2605.18401](https://arxiv.org/abs/2605.18401))がTerminal-Bench 2.0で**+7.9pp**を達成する等、生成・キュレーション・権限・進化の各方面で実証研究が並走している。

2. **Self-Evolving Agents の "実用化" 段階への移行**
   `Ratchet`([2605.22148](https://arxiv.org/abs/2605.22148)) がスキル作成ではなく「**ライフサイクル管理がボトルネック**」と明示し、結果駆動退役・アクティブキャップ・メタスキル指針・パターン正規化の4機構を提案。`EvolveMem`([2605.13941](https://arxiv.org/abs/2605.13941))は**検索基盤と知識ベースの双方を進化**させLoCoMo +25.7%/MemBench +18.9%を達成し、進化された設定がベンチマーク間で**正に転移する**ことを示した。`EvoMemBench`([2605.18421](https://arxiv.org/abs/2605.18421))がメモリ進化評価の標準化を担う。

3. **Cybersecurity Agents の本格参入**
   `Cochise`([2605.11671](https://arxiv.org/abs/2605.11671))が**597行のPython参照ハーネス**を公開し研究基盤を整備、`ExploitBench`([2605.14153](https://arxiv.org/abs/2605.14153))がV8の41バグでエクスプロイト能力を**16段階のラダー**で測定（非公開フロンティアモデルで**約50%成功率**）。防御側では`MemRepair`([2605.17444](https://arxiv.org/abs/2605.17444))がSEC-Benchで**58.0% SOTA**、`Kumushi`([2605.04251](https://arxiv.org/abs/2605.04251))が178件のC/C++脆弱性で専用APRを上回る。

4. **長期運用での "記憶の腐敗" 問題の発見**
   `Useful Memories Become Faulty`([2605.12978](https://arxiv.org/abs/2605.12978))が**GPT-5.4が以前解けたARC-AGI問題の54%で失敗**することを発見し、原因は元経験ではなく**統合プロセス自体**にあると突き止めた。`STALE`([2605.06527](https://arxiv.org/abs/2605.06527))では**最良モデルでも陳腐化検出精度55.2%**にとどまり、Implicit Conflictという新しい失敗モードを特定。`Rethinking How to Remember`([2605.19952](https://arxiv.org/abs/2605.19952))は原子事実中心設計の限界を指摘し**3表現併用**を提案。

横断的な共通課題は次の3点に集約される:
1. **長期運用における腐敗（メモリ・スキル・ワークフロー）の検出と修復**
2. **「失敗帰属（failure attribution）」の構造化**（`Beyond Individual Intelligence`([2605.14892](https://arxiv.org/abs/2605.14892))が "LIFE" フレームワークで主題化）
3. **行動評価では捉えられない安全特性の保証**（`Position: Behavioural Assurance`([2605.15164](https://arxiv.org/abs/2605.15164))が21のガバナンス文書を分析しメカニスティック解釈性への移行を提唱）

## 1. Skills 研究の独立宣言

### 1.1 このジャンルのトレンドと課題感

🔍 2024年までのエージェント研究は **(a) ツール呼び出し** と **(b) ワークフロー設計** が主軸だった。Anthropic が2025年末に提唱した「Agent Skills」は、5月の `A Comprehensive Survey on Agent Skills` で正式に **「ツール・メモリ・実行時コンテキストをタスク特化制約下で協調させる再利用可能な手続き的アーティファクト」** として定義され、推論・計画の上に位置する**運用実行レイヤ**であると論じられた。これにより、**生成・キュレーション・監査・赤チーム化・分類学**という研究分野としての全構成要素が同時並行で立ち上がった。残課題は、**スキル流通の標準化**と**進化過程の安全性保証**である。

### 1.2 スキルの分類学・サーベイ

#### [May 2026] "A Comprehensive Survey on Agent Skills: Taxonomy, Techniques, and Applications" [[paper](https://arxiv.org/abs/2605.07358)] 📖

- **概要**: 著者 Yingli Zhou, Wang Shu, Yaodong Su 他(中国の研究グループ)による包括サーベイ。Agent Skills を **表現・獲得・検索・進化**の4フェーズで整理し、推論・計画の上位レイヤとしてのSkillが信頼性と構成可能性に不可欠であることを論じる。
- **差分・新規性**: 2月の `Agent Skills for Large Language Models: Architecture, Acquisition, Security`(2602.12430) が概念紹介中心だったのに対し、本サーベイは **品質管理・相互運用性・安全な更新・長期能力管理**という運用視点を明示的に組み込んだ最初期の包括的整理。今後のSkill研究の参照文献として機能する。

### 1.3 推論を内側のスキルとして扱う

#### [May 2026] "HeavySkill: Heavy Thinking as the Inner Skill in Agentic Harness" [[paper](https://arxiv.org/abs/2605.02396)]

- **概要**: 著者 Jianing Wang 他。深い推論（Heavy Thinking）を**外部オーケストレーションではなくLLM内部の能力として内在化**するフレームワーク。「並列推論→要約」という2段階処理を提案し、Best-of-Nなど従来の選択手法を上回ることを実証。RLによって推論の広さと深さを同時に強化できる。
- **差分・新規性**: 既存のスキル研究は「外部ツールの抽象化」がほとんどだったのに対し、本研究は**推論プロセスそのものをスキルとして扱う**点が新しい。脆弱な外部協調系に依存せず自律的に複雑問題解決を改善する「inner skill」という新パラダイムを提示。`Tools as Continuous Flow`([2605.07339](https://arxiv.org/abs/2605.07339)) の連続フロー化思想と通底する。

### 1.4 スキルの生成・キュレーション

#### [May 2026] "SkillGenBench: Benchmarking Skill Generation Pipelines for LLM Agents" [[paper](https://arxiv.org/abs/2605.18693)] ⚖️

- **概要**: 著者 Yifan Zhou 他。既存スキルの**利用ではなく、リポジトリやドキュメントから正しく再利用可能で実行可能なスキルを生成できるか**を評価するベンチマーク。**タスク条件付き生成 vs タスク非依存生成**の2シナリオ、**リポジトリ基盤 vs ドキュメント基盤**の2手続きソースをカバーする。
- **差分・新規性**: 4月の `SKILLFLOW`(2604.17308) が「発見・進化」を測ったのに対し、本ベンチは**生成パイプライン**の品質を測るmeta-benchmark。リポジトリ由来とドキュメント由来で**異なる失敗パターン**が現れることを実証した点が貢献。

#### [May 2026] "SkillOS: Learning Skill Curation for Self-Evolving Agents" [[paper](https://arxiv.org/abs/2605.06614)]

- **概要**: 著者 Siru Ouyang 他（Tomas Pfister/George Lee含む大規模グループ）。**凍結エージェント実行器と訓練可能なスキルキュレーター**を組み合わせ、複合報酬と関連タスクの戦略的グループ化で学習信号を生成するRLフレームワーク。学習されたキュレーターは異なるエージェントアーキテクチャやドメインに汎化し、キュレートされたスキルが時間とともに複雑な構造化知識へ発展する。
- **差分・新規性**: 既存のスキル研究は **「スキルを発見する」** が中心だったが、本研究は**何を残し何を捨てるかの判断自体を学習対象**にする。Self-Evolutionとの接続が明確で、`SkillsVote`([2605.18401](https://arxiv.org/abs/2605.18401))のガバナンス系と相補的。

#### [May 2026] "SkillsVote: Lifecycle Governance of Agent Skills from Collection, Recommendation to Evolution" [[paper](https://arxiv.org/abs/2605.18401)]

- **概要**: 著者 Hongyi Liu 他。Agent Skillsを **「実行可能スクリプト＋手続きガイダンス」の経験スキーマ**として扱い、収集→推薦→進化のライフサイクルを管理するガバナンスフレームワーク。OSSリポジトリから環境要件と品質指標を解析、実行後にトレースをスキル連結サブタスクに分解し、**成功した発見のみライブラリ更新を許可**する設計。Terminal-Bench 2.0で**最大+7.9pp**、SWE-Bench Proで**最大+2.6pp**改善。
- **差分・新規性**: **凍結エージェントの再訓練なしに、外部スキルライブラリで強化できる**ことを実証した点が実用上重要。スキルを「投票」によりライフサイクル管理する発想は、ソフトウェア工学のパッケージレジストリの統治モデルに近い。

#### [May 2026] "SkillFlow: Flow-Driven Recursive Skill Evolution for Agentic Orchestration" [[paper](https://arxiv.org/abs/2605.14089)]

- **概要**: 著者 Mingda Zhang 他。訓練可能なSupervisorと動的スキルライブラリ・凍結実行器の構造化環境で、多ターン対話によりタスクオーケストレーションを自動化する。**Tempered Trajectory Balance損失で多様性を保ち**、逆方向ポリシーで透明な信用割当を実現。意思決定ギャップに基づきスキルの**作成・修正・除去を自律判断する再帰的進化機構**を提案。QA・数学・コード・対話的意思決定の14データセットで大幅改善。
- **差分・新規性**: スキル進化を**フロー（連続的な変更履歴）として再帰的に駆動**する点が独自。Multi-Agentセクションの `Recursive Agent Optimization`([2605.06639](https://arxiv.org/abs/2605.06639)) と「**再帰性**」をキーワードとして共有する。

### 1.5 スキルの権限・セキュリティ

#### [May 2026] "SkillScope: Toward Fine-Grained Least-Privilege Enforcement for Agent Skills" [[paper](https://arxiv.org/abs/2605.05868)]

- **概要**: 著者 Jiangrong Wu 他。Agent Skillsが最小権限原則を超えた過剰な動作を行うセキュリティリスクに対応する**グラフベース解析手法**。命令レベル手続きとコードレベル操作を**細粒度アクションノード**としてモデル化し、タスク特化リプレイで検証、制御フロー機構で有害動作を制約する。スキル過剰権限検出で**F1=94.53%**、現実の**7,039スキル**で違反を検証し、**過剰権限発動を88.56%削減**しながら正規タスク完了を維持。
- **差分・新規性**: 従来のRBAC的役割ベース管理ではなく、**スキル単位の宣言型最小権限**という新しい粒度を提示。7,039 スキルという実世界スケールでの検証は他に類を見ない。Cybersecurity の `Trust No Tool`([2605.17453](https://arxiv.org/abs/2605.17453)) と思想を共有する **「スキル自体が攻撃ベクタになる」** 前提を運用に持ち込む。

#### [May 2026] "Counterfactual Trace Auditing of LLM Agent Skills" [[paper](https://arxiv.org/abs/2605.11946)]

- **概要**: 著者 Xiaolin Zhou, Jinbo Liu, Li Li, Ryan A. Rossi(Adobe), Xiyang Hu。**スキルあり/なしのエージェント実行トレースをペアで対比**し、フェーズ分割と構造化アノテーションで挙動変化を可視化するフレームワーク。49個のSWEタスクで、**合格率改善はわずか+0.3%でも、テンプレ丸写し・タスク外成果物生成・過剰計画・タスク回復など522件の挙動変化を検出**。
- **差分・新規性**: 従来メトリクス（成功率、コスト）では見逃される失敗モードを再現可能に測定。**特に高ベースラインで飽和したタスクでの隠れた挙動シフト**を定量化する点が、Multi-Agentの failure attribution 課題（`Beyond Individual Intelligence`[2605.14892](https://arxiv.org/abs/2605.14892)）とも連動する。

### 1.6 横断的示唆

スキル研究の急速な分化は、ソフトウェア工学における**「パッケージ管理の歴史」をなぞっている**。生成→キュレーション→権限→赤チーム→ユーザ理解、という発展軸が同時並行で動いている。

実装者向けTips:
1. スキルは**バージョン管理可能なアーティファクト**として扱う（`Code as Agent Harness`[2605.18747](https://arxiv.org/abs/2605.18747)の発想）。
2. **トリガー条件と権限を仕様レベルで明示**する（`SkillScope` の最小権限実装）。
3. **使用トレースを全保存**し、後で counterfactual 監査が可能な状態にする（`Counterfactual Trace Auditing`）。
4. **退役（retirement）機構を最初から組み込む**（`Ratchet` および `SkillsVote` の示唆）。

## 2. Self-Evolution: 「進化させる」から「進化を統治する」へ

### 2.1 このジャンルのトレンドと課題感

🔍 2025年Q4〜2026年Q1の進化エージェント研究は**「もっと進化させる」競争**だった。今期は **「進化の副作用を制御する」** 方向に明確にシフトしている。`Ratchet`([2605.22148](https://arxiv.org/abs/2605.22148))が「**ライフサイクル管理こそボトルネック**」と明示し、`EvolveMem`([2605.13941](https://arxiv.org/abs/2605.13941))が**検索機構自体を進化**させ、`EvoMemBench`([2605.18421](https://arxiv.org/abs/2605.18421))が評価軸を整備した。残課題は、**進化の収束条件と長期安定性**の保証。

### 2.2 進化の衛生（Hygiene）

#### [May 2026] "Ratchet: A Minimal Hygiene Recipe for Self-Evolving LLM Agents" [[paper](https://arxiv.org/abs/2605.22148)]

- **概要**: 著者 Xing Zhang 他。**自己進化型スキルライブラリのボトルネックはスキル作成ではなくライフサイクル管理である**と指摘。単一エージェントが自然言語スキルを書き・検索し・キュレートし・退役させる仕組みで、**結果駆動退役・アクティブキャップ・メタスキル指針・パターン正規化**の4機構を備える。MBPP+ hard-100でClaude Opus 4.7を使い**+0.328改善**、退役とメタスキル作成の必須性を**8つのアブレーション**で検証、**ベースライン以下に劣化しないことを数学的命題で保証**。
- **差分・新規性**: 既存の自己進化研究は「進化能力の上限」を競っていたのに対し、本研究は **「進化の下限保証」** を提案。「ラチェット（一方向締め付け）」という命名通り、**進化を後戻りさせない最小限の制約**を提供。今後のself-evolving agentデプロイの事実上の必須コンポーネントになる可能性が高い。

### 2.3 進化過程の評価

#### [May 2026] "EvoMemBench: Benchmarking Agent Memory from a Self-Evolving Perspective" [[paper](https://arxiv.org/abs/2605.18421)] ⚖️

- **概要**: 著者 Yuyao Wang 他。**記憶スコープ（in-episode vs cross-episode）と記憶内容（knowledge-oriented vs execution-oriented）**の2軸で構成した包括的メモリ評価フレームワーク。15種のメモリ手法と長文脈モデルを標準化テストで評価。
- **差分・新規性**: 重要な経験的発見として、**現代のメモリシステムに万能性はない**（直近文脈が不十分または高難度タスク時に最も有効）。**検索ベースは知識集約型に強く、経験/手続き的メモリは実行タスクで優れる**ことを実証。これはメモリ手法選択の指針として実用上極めて重要。

### 2.4 進化アーキテクチャの新展開

#### [May 2026] "EvolveMem: Self-Evolving Memory Architecture via AutoResearch for LLM Agents" [[paper](https://arxiv.org/abs/2605.13941)]

- **概要**: 著者 Jiaqi Liu, Xinyu Ye 他。**検索基盤を固定したまま記憶内容のみを更新する従来手法を超え、知識ベースと検索機構の双方を進化**させる自己進化メモリアーキテクチャ。LLM診断モジュールが**検索設定を行動空間として最適化**し、**ガード付きメタ解析器が有害変更を自動巻き戻す**。LoCoMoで**25.7%**、MemBenchで**18.9%**の改善。
- **差分・新規性**: 4月までのメモリ進化研究は「内容更新」にとどまっていたが、本研究は**機構自体の進化**を扱う一段上のメタレベル。**進化された設定がベンチマーク間で正に転移**することを示しており、**普遍的な検索原理が発見されている可能性**を示唆する点で重要。

#### [May 2026] "Harnessing Agentic Evolution" [[paper](https://arxiv.org/abs/2605.13821)]

- **概要**: 著者 Jiayi Zhang 他(MetaGPT/DeepWisdomチーム関係者を含む)。**AEvoはエージェント進化を対話環境として扱い**、累積進化コンテキストをプロセスレベルの状態として用いる。メタエージェントが候補を直接提案する代わりに**手順やエージェントコンテキストを編集**する。手順型・エージェント型双方の手法に対応。
- **差分・新規性**: 最強ベースラインに対し **26%の相対改善**、3つのオープンエンド最適化タスクでSOTA。「進化を対話環境として扱う」という抽象化が独自で、強化学習の枠組みで進化を扱えるようになる。

### 2.5 自己進化型検索

#### [May 2026] "Towards Self-Evolving Agentic Literature Retrieval" [[paper](https://arxiv.org/abs/2605.14306)]

- **概要**: 著者 Yuwen Du, Tian Jin 他。学術文献検索のための**PaSaMaster**システム。**(1) ランク付け証拠を用いた反復改善**、**(2) 論文生成ではなくランキングによるソース幻覚防止**、**(3) 意図解析のみ高性能LLMを使い検索は軽量モデルに委譲**する3機構で動作。**38分野でキーワード検索比15.6倍のF1**、**ソース幻覚ゼロ**、**GPT-5.2を上回りつつ計算資源は1%のみ**。
- **差分・新規性**: 1月の `PaSa`(2501.10120) の発展形で、効率性とソース信頼性を両立。Deep Researchセクションでも参照される横断的論文。

### 2.6 横断的示唆

Self-Evolution の今期トレンドは **「能力の最大化」から「進化の信頼性」**。実装者向けTips:

1. **進化の前後で不変条件をテスト**: `Ratchet` の数学的保証の発想を実装に取り込む。
2. **退役（retirement）機構を最初から組み込む**: `Ratchet` の8アブレーションで退役の必須性が示された。
3. **進化機構自体の汎化を確認**: `EvolveMem` の知見通り、**進化された設定の転移性**は重要なシグナル。
4. **進化を「対話環境」として抽象化**: `Harnessing Agentic Evolution`(AEvo) の発想は強化学習との接続を可能にする。

## 3. メモリ研究の二極化：楽観と幻滅

### 3.1 このジャンルのトレンドと課題感

🔍 4月のメモリ研究は**「現状のメモリは記憶ではなくメモ（memo）に過ぎない」**という根源的問題提起（`Contextual Agentic Memory is a Memo`[2604.27707](https://arxiv.org/abs/2604.27707)）で締めくくられた。5月はこの問題提起への**実証的応答**として、**(A) 悲観派**（メモリの妥当性・腐敗を疑う）と **(B) 楽観派**（より構造化・モデル化されたメモリを作る）の二極化が顕著に。残課題は、両派の知見をどう統合した運用設計に落とすか。

### 3.2 悲観派：メモリ腐敗の実証発見

#### [May 2026] "Useful Memories Become Faulty When Continuously Updated by LLMs" [[paper](https://arxiv.org/abs/2605.12978)] 🔥

- **概要**: 著者 Dylan Zhang, Yanshan Lin 他。**LLMによる経験統合型メモリが「最初は有用性が上がるがやがて劣化し、メモリなしベースラインを下回る」現象を発見**。**GPT-5.4は統合メモリ使用時、以前解けたARC-AGI問題の54%で失敗**。原因解析の結果、**元経験ではなく統合プロセス自体に問題**があると突き止めた。
- **差分・新規性**: メモリ研究はこれまで「より良く更新する」競争だったが、本研究は **「そもそも更新の仕方が壊している」** ことを実証する反論。提言として、**生のエピソードを一級証拠として保持し、毎回の対話後ではなく明示的にゲートして統合すべき**と主張。**元証拠を上書きしない統合能力**が、頑健なエージェントメモリの必要条件であると結論。これは2026年下半期のメモリ設計に決定的な影響を与える可能性がある重要論文。

#### [May 2026] "STALE: Can LLM Agents Know When Their Memories Are No Longer Valid?" [[paper](https://arxiv.org/abs/2605.06527)] ⚖️

- **概要**: 著者 Hanxiang Chao, Yihan Bai, Rui Sheng, Tianle Li, Yushi Sun。**新しい観測が明示的否定なしに過去記憶と矛盾する「Implicit Conflict」を重要な失敗モードとして特定**。**400の専門家検証済みシナリオ・1,200クエリ**で、(1)陳腐化検出、(2)偽前提の拒否、(3)更新情報の将来適用の3能力を評価。**最良モデルでも全体精度55.2%**にとどまる。
- **差分・新規性**: 「メモリの正しさ」ではなく **「メモリの妥当性ウィンドウの認識」** を測る初のベンチマーク。**CUPMemプロトタイプ**を提案し、**構造化状態統合で記憶改訂を改善**できることを示す。明示的状態管理が信頼性ある記憶への道筋であると結論。

#### [May 2026] "Rethinking How to Remember: Beyond Atomic Facts in Lifelong LLM Agent Memory" [[paper](https://arxiv.org/abs/2605.19952)]

- **概要**: 著者 Jingwei Sun 他。原子事実中心の既存メモリ設計が**細部を失う問題**に対し、**生の対話セグメント・原子事実・合成プロファイル**の3つの相補的表現を持つ**TriMem**を提案。**TextGradベースのプロンプト最適化**により応答フィードバックで抽出処理を継続的に洗練する。LoCoMoとPerLTQAで既存手法を上回った。
- **差分・新規性**: 4月の `To Know is to Construct (SCG-MEM)`(2604.20117) が**スキーマ制約**で表現問題に対処したのに対し、本研究は**原子的事実モデル**自体を疑い、**3表現併用**を解とする一段深い問題提起。パラメータ更新なしでメモリ抽出を最適化する点も実用的。

### 3.3 楽観派：構造化・モデル化されたメモリ

#### [May 2026] "MeMo: Memory as a Model" [[paper](https://arxiv.org/abs/2605.15156)]

- **概要**: 著者 Ryan Wei Heng Quek, Sanghyuk Lee 他（Daniela Rus/Armando Solar-Lezama含むMITグループ）。**LLM本体を変更せず、新規・専門知識を別個のメモリコンポーネントとしてエンコード**するモジュール型フレームワーク。**(1)複数文書横断の複雑関係を捉える**、**(2)検索ノイズに頑健**、**(3)知識消失を防ぐ**、**(4)オープン/プロプライエタリLLM双方と重みアクセスなしで連携**、**(5)推論時の検索効率がコーパスサイズに依存しない**。BrowseComp-Plus, NarrativeQA, MuSiQueの3ベンチで再訓練不要かつ検索ノイズ堅牢な競争力ある性能。
- **差分・新規性**: 既存のRAG/ベクタDBが**non-parametric**なメモリだったのに対し、本研究は **メモリのモジュラー化された別モデル化**を提案。`Contextual Agentic Memory is a Memo`(2604.27707) で指摘された **「重みベース統合の欠如」** への現実的な応答と言える（完全なweight integrationには至らないが、**モジュラー化された外部モデル**として準パラメトリック化）。

#### [May 2026] "MemGym: a Long-Horizon Memory Environment for LLM Agents" [[paper](https://arxiv.org/abs/2605.20833)] ⚖️

- **概要**: 著者 Wujiang Xu 他。**既存メモリベンチがマルチターンチャットでの個人情報保持に偏っている問題**を指摘し、**ツール使用・ディープリサーチ・コーディング・コンピュータ操作を含む5つの評価トラック**を提案。**推論・検索・ツール使用能力からメモリ性能を切り離した「メモリ独立スコア」**を導入する。Qwen3-1.7Bベースの軽量報酬モデル**MemRM**も提供。
- **差分・新規性**: 既存ベンチの**評価混在問題**を解決する設計。「推論が良いからメモリが良く見える」現象を排除し、メモリそのものを公正評価。`EvoMemBench`([2605.18421](https://arxiv.org/abs/2605.18421)) と相補的な評価基盤。

#### [May 2026] "Auto-Dreamer: Learning Offline Memory Consolidation for Language Agents" [[paper](https://arxiv.org/abs/2605.20616)]

- **概要**: 著者 Chongrui Ye 他（Julian McAuley/Jiaxuan You 含む UCSD系グループ）。**高速なセッション内メモリ収集と低速なクロスセッション洗練を分離**するAuto-Dreamerを提案。**GRPOで学習**し、ScienceWorldで**7ポイント改善**しつつメモリバンクを**最強ベースラインの1/12に縮小**、ALFWorldとWebArenaに**追加学習なしで転移可能**。
- **差分・新規性**: 神経科学の「睡眠中の記憶統合」をアナロジーに、**エージェントの "休息時間" にメモリを整理・統合**する初の試み。`Contextual Agentic Memory is a Memo`(2604.27707) で示唆された二層モデル（高速セッション + 低速統合）を実装した点で意義深い。

#### [May 2026] "Tree-based Credit Assignment for Multi-Agent Memory System" [[paper](https://arxiv.org/abs/2605.04811)]

- **概要**: 著者 Marina Mao 他。**builder–summarizer–retrieval パイプラインを木構造に拡張**し、各エージェントの出力を複数の枝として展開して結果を平均化することで、**エージェント単位の貢献を推定**。長期ベンチマークで性能向上。
- **差分・新規性**: **コストの高いアノテーションを使わずに、木構造ベースのクレジット割り当てによって異種エージェントを同時に最適化**できる。Multi-Agent の failure attribution（`Beyond Individual Intelligence`[2605.14892](https://arxiv.org/abs/2605.14892)）のメモリ版とも言える。

#### [Apr 2026] "When Continual Learning Moves to Memory: A Study of Experience Reuse in LLM Agents" [[paper](https://arxiv.org/abs/2604.27003)]

- **概要**: 著者 Qisheng Hu, Quanyu Long, Wenya Wang。LLMエージェントの外部メモリにおける継続学習問題を、**経験のエンコーディングと検索のための整理**という2つの設計次元から調査する。ALFWorldとBabyAIで実験を行い、**抽象的な手続き記憶が詳細な軌跡記録より汎化**することや、**forward transferとforgettingがトレードオフ関係**にあることを示した。
- **差分・新規性**: 重要な知見として **「外部メモリは継続学習問題を解決しない、メモリの表現と検索設計の問題に再構成するだけだ」** と結論。これは「メモリさえあれば学習問題が解決する」という安易な信念への警鐘。

### 3.4 横断的示唆：メモリ設計の新しい標準

悲観派と楽観派の知見を統合すると、次の実装パターンが見える:

1. **append-only + 明示的ゲート**: `Useful Memories Become Faulty` の警告通り、自動上書きは避け、統合は明示的にゲート。
2. **`valid_until` を明示**: `STALE` の Implicit Conflict 対策として、全メモリレコードに妥当性を付与。
3. **取り出し時に "stale check"**: `STALE` の CUPMem の発想で、明示的状態管理。
4. **オフライン consolidation pass**: `Auto-Dreamer` の通り、定期的にメモリを整理・統合する batch job。
5. **3表現併用**: `Rethinking How to Remember` の TriMem 通り、原子事実だけでなく生セグメント・合成プロファイルも持つ。
6. **モジュラー化されたメモリモデル**: `MeMo` のように、メモリ自体を**別の小モデル**として扱う。長期的に RAG を置き換える可能性。

### 3.5 メモリ研究の1月→5月の流れ

```
[Jan 2026]: Agentic Memory(2601.01885), AtomMem(2601.08323) などメモリ機構ラッシュ
            ↓

            ↓

            ↓

```

## 4. Cybersecurity Agents の本格参入

### 4.1 このジャンルのトレンドと課題感

🔍 4月号の[サイバーセキュリティニュースレター](../apr_2026/cybersecurity_2025.md)では「**攻撃の永続化**」「**防御のレイヤ分化**」「**ベンチマーク群の急成立**」の3軸を整理した。5月はこれら3軸の **産業化** が現実化している。`Cochise`(参照ハーネス公開)、`ExploitBench`(16段階能力ラダー)、`MemRepair`(リポジトリ階層メモリ修復) など、**標準化と実用化の両方**が同時に進む。残課題は、**攻撃側の自律進化が防御側の対応速度を超える可能性**への対策。

### 4.2 攻撃側エージェントの研究基盤整備

#### [May 2026] "Cochise: A Reference Harness for Autonomous Penetration Testing" [[paper](https://arxiv.org/abs/2605.11671)]

- **概要**: 著者 Andreas Happe, Jürgen Cito。LLM駆動の自律ペンテスト研究のための**597行のPython参照ハーネス**Cochiseを提案。**Planner-Executorアーキテクチャ**を採用し、長期状態をLLMコンテキストから分離して保持し、**SSH経由でコマンドを自己訂正しながら実行**する。**Game of Active Directory (GOAD)** テストベッドで評価。
- **差分・新規性**: SOTAツールではなく、**モデル・アーキテクチャ・手法を比較研究するための再利用可能な実験基盤**として位置づける明示的な設計。**軌跡ログ・解析ユーティリティ**を公開。これは Cybersecurity 版の `OpenHands`(2407.16741) とも言え、今後の攻撃側研究の事実上のベースラインになる可能性。

#### [May 2026] "Pen-Strategist: A Reasoning Framework for Penetration Testing Strategy Formation and Analysis" [[paper](https://arxiv.org/abs/2605.04499)]

- **概要**: 著者 Yasod Ginige 他。**ファインチューニングされたQwen-3-14B**でテスト戦略を論理的推論によって生成し、戦略を実行可能アクションに変換する分類器と組み合わせるドメイン特化推論モデル。**戦略導出でベースライン比87%向上、PentestGPT統合時にサブタスク完了率47.5%向上、CTFKnowで18%向上**。
- **差分・新規性**: 既存のペンテストエージェントは「ツール呼び出し」レベルの実装が中心だったが、本研究は**戦略レベルの推論をドメイン特化モデルに切り出す**点が新しい。商用LLMを上回る性能を**14Bモデル**で達成した点も実用上重要。

#### [May 2026] "From Controlled to the Wild: Evaluation of Pentesting Agents for the Real-World" [[paper](https://arxiv.org/abs/2605.10834)]

- **概要**: 著者 Pedro Conde 他。**CTFのような事前定義目標に依存せず、複雑な実環境ターゲットでの「検証済み脆弱性発見」**に焦点を当てた評価プロトコル。**構造化グラウンドトゥルース、LLMベース意味マッチング、二部グラフ解決、効率指標**を組み合わせる。
- **差分・新規性**: **専門家アノテーション付きグラウンドトゥルースと再現可能なコードを公開**し、実世界条件下でのAIペンテスト評価を可能にした点。`WildClawBench`([2605.10912](https://arxiv.org/abs/2605.10912)) と思想を共有する「Wild benchmark」潮流の一部。

#### [May 2026] "Autonomous LLM Agents & CTFs: A Second Look" [[paper](https://arxiv.org/abs/2605.21497)]

- **概要**: 著者 Youness Bouchari, Matteo Boffa, Marco Mellia 他。**LLMエージェントが人間に近いレベルでセキュリティ課題を解くという主張を再検証**し、複数のエージェント設計を**14の脆弱性カテゴリにわたる30のWeb CTF**で評価。**汎用エージェントclaude-codeが工学的システムと同等の19/30を解決**し、**専門設計エージェントが一貫性と効率でモノリシック設計を上回る**ことを示した。
- **差分・新規性**: 再現性研究は珍しいが重要。AIエージェント研究全体で**ベンチマーク汚染**や**評価条件の差異**が問題化している中、サイバーセキュリティドメインで明示的に再検証。**「現状エージェントが人間レベルに達しない持続的障壁」** を実証的に整理。

### 4.3 ベンチマーク・能力ラダー

#### [May 2026] "ExploitBench: A Capability Ladder Benchmark for LLM Cybersecurity Agents" [[paper](https://arxiv.org/abs/2605.14153)] ⚖️

- **概要**: 著者 Seunghyun Lee, David Brumley（CMUの著名なセキュリティ研究者）。エクスプロイト成功を二値ではなく、**カバレッジ・クラッシュからサンドボックスプリミティブ、任意の読み書き、制御フロー乗っ取り、任意コード実行までの16段階に分解**するベンチマーク。**41のV8バグ**を評価し、**ランダム化チャレンジレスポンスや差分実行解析で決定論的検証**を行う。
- **差分・新規性**: **公開モデルは脆弱コードに到達しクラッシュさせるが、任意コード実行は限定的**で、**非公開フロンティアモデルが約50%の成功率**を示すことを定量化。**エクスプロイト構築を「新興フロンティア能力」と位置付けた点が重要**で、今後の AI 規制議論の中心的指標となる可能性が高い。

#### [May 2026] "CyBiasBench: Benchmarking Bias in LLM Agents for Cyber-Attack Scenarios" [[paper](https://arxiv.org/abs/2605.07830)] ⚖️

- **概要**: 著者 Taein Lim 他。攻撃的サイバーセキュリティタスクで**各LLMエージェントが特定の攻撃ファミリーに偏ること**を発見し、**5エージェント・3ターゲット・4プロンプト条件・10攻撃ファミリーにわたる630セッション**のベンチマークCyBiasBenchを構築。**エージェントが偏りに反する攻撃へのリダイレクトに抵抗する「バイアスモメンタム効果」**を特定。
- **差分・新規性**: 攻撃能力そのものではなく**攻撃の偏り**を測る初のベンチ。**「エージェント攻撃者がどこを狙いがちか」** を知ることで防御の優先順位を決められる、防御側にとって重要な情報源。

### 4.4 防御側エージェント

#### [May 2026] "MemRepair: Hierarchical Memory for Agentic Repository-Level Vulnerability Repair" [[paper](https://arxiv.org/abs/2605.17444)]

- **概要**: 著者 Simiao Liu 他。**History-Fix、Security-Pattern、Refinement-Trajectory の3つのメモリ要素**とフィードバック駆動の洗練プロセスを統合したエージェント枠組み。**SEC-Bench 58.0%、PatchEval 58.2%、Multi-SWE-bench 30.58% のSOTA**を達成し、OpenHandsやSWE-agentを上回った。
- **差分・新規性**: 脆弱性修復を**反復的・経験駆動タスク**として扱い、3階層のメモリで多言語のリポジトリ規模修復に対応。`Kumushi`([2605.04251](https://arxiv.org/abs/2605.04251)) と組み合わせると、「**根本原因をリポジトリ階層メモリで特定し、修復する**」一貫した方法論が形成される。

#### [May 2026] "Root-Cause-Driven Automated Vulnerability Repair (Kumushi)" [[paper](https://arxiv.org/abs/2605.04251)]

- **概要**: 著者 Hulin Wang 他（Adam Doupé, Yan Shoshitaishvili 等 ASU/著名セキュリティ研究者）。**LLMベースの脆弱性修復が症状を覆い隠す表面的編集をしがち**な問題に対し、**多様化した動的フォルトローカライゼーション**と**エビデンス重み付けランキング**を組み合わせたエージェント Kumushi。**178のC/C++脆弱性で専用修復エージェントを上回り、商用コーディングツールに匹敵**する性能。
- **差分・新規性**: 既存の APR (Automated Program Repair) はテスト通過ベースのパッチ生成が中心だったが、本研究は **「なぜこのバグが発生したか」** の因果分析を起点とする。**自動検証と専門家評価を組み合わせた二層評価指標**を導入。

#### [May 2026] "Generating Proof-of-Vulnerability Tests to Help Enhance the Security of Complex Software" [[paper](https://arxiv.org/abs/2605.03956)]

- **概要**: 著者 Shravya Kanchi 他。**脆弱な依存関係が実際にリスクを与えるかを判定**するため、**コールパス解析とLLMを組み合わせてProof-of-Vulnerabilityテストを自動生成**する**PoVSmith**を提案。**33のJavaアプリ・ライブラリペアで脆弱なAPIを呼び出す152のエントリーポイントを特定**し、**生成された152のテストのうち84(55%)が実際の攻撃ベクトルを実証**した。
- **差分・新規性**: 既存の SAST/DAST が**脆弱性の指摘止まり**だったのに対し、本研究は**再現可能な証明**まで提供する。**エージェントベースのテスト生成、実行フィードバックによる反復洗練、LLM駆動の品質評価**を組み合わせ、人手介入を削減しつつテスト品質を向上。

### 4.5 産業化への警告

#### [May 2026] "Agentic AI and the Industrialization of Cyber Offense: Forecast, Consequences, and Defensive Priorities for Enterprises and the Mittelstand" [[paper](https://arxiv.org/abs/2605.06713)]

- **概要**: 著者 Christopher Koch（単著、ドイツ系研究者）。エージェント型AIが**偵察、フィッシング、認証情報悪用、脆弱性トリアージ、エクスプロイト適応**などのコストを下げ攻撃ライフサイクルを圧縮する点に焦点を当てる。**Three Channel Agentic Cyber Risk Model**と**Agentic Attack Compression Model**を提示し、**2026年Linuxカーネル「Copy Fail」事件を分析**、**2028年までの予測**を行う。
- **差分・新規性**: 学術的攻撃手法研究ではなく、**産業界・特にドイツ・欧州のMittelstand（中堅企業）向けの戦略提言**という珍しい論調。**アイデンティティ管理やパッチ管理速度、エージェントガバナンス**などの防御優先事項を提示。AI規制議論で参照される可能性が高い。

### 4.6 横断的示唆

サイバーセキュリティ分野は **「研究 → 産業化」のフェーズ移行が最も速い**領域になっている。実装者向けTips:

1. **`Cochise` のような Reference Harness を採用**: 自作するより既存の検証済み実装をベースに。
2. **`ExploitBench` の16段階ラダーで自社モデルを評価**: 規制議論への準備にもなる。
3. **`MemRepair` の3階層メモリ（History-Fix/Security-Pattern/Refinement-Trajectory）** は脆弱性修復だけでなく、リポジトリ全体の理解にも応用可能。
4. **`Generating Proof-of-Vulnerability Tests` の再現テスト生成**は CI/CD への組み込みが効果的。
5. **中堅企業はアイデンティティ管理とパッチ管理速度を再強化**（`Agentic AI and the Industrialization of Cyber Offense` の提言）。

## 5. Software Agents: 保守と根本原因への重心移動

### 5.1 このジャンルのトレンドと課題感

🔍 2024〜2025年の Software Agents 研究は **「コード生成」競争**（SWE-bench 系の SOTA レース）が主軸だった。今期は明確に**「コードのライフサイクル全体」**（生成→レビュー→保守→修復）への関心移行が起きている。背景には、**エージェント生成コードの実運用での問題**が現実化していることがある。

### 5.2 エージェント生成コードの保守問題の実証

#### [May 2026] "To What Extent Does Agent-generated Code Require Maintenance? An Empirical Study" [[paper](https://arxiv.org/abs/2605.06464)]

- **概要**: 著者 Shota Sawada 他（NAIST系日本グループ）。**AIDevデータセット**を用い、**100の人気リポジトリから1,000以上のファイルと約3,200の修正**を分析し、AI生成コードと人間が書いたコードの保守頻度を比較。**(1) LLMエージェント生成コードは人間生成より保守頻度が低い**、**(2) 変更はファイル内容の僅かな部分にとどまる**、**(3) AIコードは機能追加が中心である一方、人間はバグ修正を優先**、**(4) 保守作業の大半は開発チームが担当**。
- **差分・新規性**: 既存研究は「**生成時点の品質**」（テスト通過率、コードスタイル等）が中心だったが、本研究は**運用後の保守コスト**という見落とされがちな指標を測定する empirical study。`Beyond Bug Fixes`(2601.20109) や `How do Agents Refactor`(2601.20160) と並ぶ「エージェント生成コードの社会的影響」研究の流れ。

### 5.3 データ合成のスケーリング

#### [May 2026] "FrontierSmith: Synthesizing Open-Ended Coding Problems at Scale" [[paper](https://arxiv.org/abs/2605.14445)]

- **概要**: 著者 Runyuan He 他（Joseph E. Gonzalez(Berkeley)/Alex Dimakis/Alvin Cheung等の大規模グループ）。**競技プログラミング課題を、目標変更・出力制約・入力一般化により改変し、オープンエンドなコーディング問題を自動合成**するシステム。**発散度メトリクス**により異なる解法を要する変種を抽出し、テストケース生成と検証を行う。**Qwen3.5-9BがFrontierCSで+8.82、ALE-benchで+306.36、Qwen3.5-27BがそれぞれそれぞれFrontierCSで+12.12、ALE-benchで+309.12の改善**を達成。
- **差分・新規性**: 既存のコーディング問題合成（HumanEval/MBPP拡張）は閉じた形式が中心だったが、本研究は**オープンエンド**を主題化。**ALE-bench で +309 という大幅改善**は学習データ合成の有効性を示す重要なシグナル。

### 5.4 横断的示唆

実装者向けTips:
1. **エージェント生成コードの保守性を独立評価**: 単に動くだけでなく、6ヶ月後の修正容易性を測る。
2. **AI生成コードは「機能追加中心」、人間コードは「バグ修正中心」** という分業傾向を運用設計に反映。
3. **合成データのスケーリングが学習に効く**（`FrontierSmith` のALE-bench +309 ppt）が、**将来のベンチマーク汚染**リスクも認識。

## 6. Deep Research / Retrieval: 長期化と単一クエリ化

### 6.1 このジャンルのトレンドと課題感

🔍 Deep Research 系の研究は3〜4月にかけて**ベンチマークラッシュ**を経験し、評価基盤が整った。5月は「次の能力境界」を探る研究が中心。特に **(1) 長期検索のコンテキスト管理**、**(2) エンタープライズ知識への適応**、**(3) 多段階検索の単一段階への圧縮** の3軸が顕在化。

### 6.2 長期検索のコンテキスト管理

#### [May 2026] "LongSeeker: Elastic Context Orchestration for Long-Horizon Search Agents" [[paper](https://arxiv.org/abs/2605.05191)]

- **概要**: 著者 Yijun Lu, Rui Ye 他。長期探索エージェントの作業コンテキスト管理課題に対し、**Skip/Compress/Rollback/Snippet/Delete の5操作**を備える**Context-ReAct**を提案し、**タスク関連性に基づきトラジェクトリを動的に整形**する。**Qwen3-30B-A3B**からファインチューンしたモデルが、**BrowseComp で 61.5%、BrowseComp-ZH で 62.5%** を達成。
- **差分・新規性**: 既存の long-context 手法は **静的な圧縮**（要約、トリミング）が中心だったが、本研究は**タスクの進行状態に応じた5種類の動的編集**を提案。Reasoning セクションでも引用される横断的論文で、**Long-Horizon タスクの基本要素技術**として位置づく。

### 6.3 エンタープライズ知識への適応

#### [May 2026] "AgenticRAG: Agentic Retrieval for Enterprise Knowledge Bases" [[paper](https://arxiv.org/abs/2605.05538)]

- **概要**: 著者 Susheel Suresh 他。エンタープライズ向けRAGを強化するため、**search/find/open/summarize の複数ツール**を備え反復的検索と文書解析を行うエージェント。**BRIGHT で 49.6% recall@1 (+21.8pp)、WixQA で 0.96 のファクト性、FinanceBench で 92% の回答正解率**を達成。
- **差分・新規性**: 重要な経験的結論として、**単段階検索からエージェント的ツール利用への移行が最大の性能向上をもたらす**ことを示した。エンタープライズコンテキストでの実用研究として、`Beyond Text-to-SQL`([2605.21027](https://arxiv.org/abs/2605.21027)) と並ぶ位置づけ。

### 6.4 多段階検索の単一段階圧縮

#### [May 2026] "Superintelligent Retrieval Agent: The Next Frontier of Information Retrieval (SIRA)" [[paper](https://arxiv.org/abs/2605.06647)] 🔥

- **概要**: 著者 Zeyu Yang, Qi Ma 他（Anshumali Shrivastava 含む Rice大グループ）。**複数ラウンドの探索的検索を、コーパス識別的な単一の検索アクションに圧縮**する**SIRA**を提案。**LLMで拡張した文書語彙・クエリ側の語彙予測・ドキュメント頻度フィルタリング**を組み合わせ、**BEIRベンチマークで多段階検索を上回る性能**を達成。
- **差分・新規性**: 「Superintelligent」というやや大胆な命名だが、内容は **学習不要かつ解釈可能な単一語彙クエリで多段階検索を凌駕する**効率的IR手法。多段階エージェント検索のコスト問題への現実的応答。これは Deep Research のアーキテクチャ議論に大きな影響を与える可能性。

### 6.5 自己進化型文献検索

`Towards Self-Evolving Agentic Literature Retrieval (PaSaMaster)`([2605.14306](https://arxiv.org/abs/2605.14306))は Self-Evolution セクション(2.5)で詳述。**38分野でキーワード検索比15.6倍のF1**、**GPT-5.2を上回りつつ計算資源は1%**という効率性が特筆される。

### 6.6 横断的示唆

実装者向けTips:
1. **コンテキスト管理を弾性的に**: `LongSeeker` の5編集操作（Skip/Compress/Rollback/Snippet/Delete）を採用検討。
2. **「単段階→エージェント的ツール利用」が最大の性能向上源**（`AgenticRAG` の知見）。
3. **多段階検索の単一段階圧縮で大幅コスト削減**: `SIRA` の発想で運用コストを下げられる。
4. **特定タスクへの最適化が進化として現れる**: `PaSaMaster` の知見で、汎用 vs 特化のバランス設計。

## 7. Multi-Agent / Orchestration: ベイズ整合性と失敗帰属

### 7.1 このジャンルのトレンドと課題感

🔍 Multi-Agent 研究は2024〜2025年に **(a) フレームワーク**、**(b) オーケストレーション最適化**、**(c) 評価** の3段階を経た。今期は **理論的基盤**（ベイズ整合性）と **運用問題**（失敗帰属、状態管理）が主題化されている。

### 7.2 理論的基盤の提案

#### [May 2026] "Position: agentic AI orchestration should be Bayes-consistent" [[paper](https://arxiv.org/abs/2605.00742)] 🔥

- **概要**: 著者 Theodore Papamarkou, Pierre Alquier, Matthias Bauer, Wray Buntine 等（**ベイズ統計学界の大物多数を含む大規模共著**）。LLMが予測・推論で優れる一方で、**多くの実応用は不確実性下の意思決定を伴う**と指摘し、**ベイズ決定理論に基づくオーケストレーション層の構築**を主張するポジションペーパー。重要な提案として、**LLMそのものをベイズエンジン化するのではなく、オーケストレーション層でベイズ原則を適用**し**較正された信念と効用認識ポリシー**を実現することを提案。
- **差分・新規性**: 既存の Multi-Agent 研究は**経験的・工学的アプローチ**が主流だったが、本研究は**統計理論からの規範**を提示する。**LLM内部ではなくオーケストレーション層でベイズ性を担保**という設計選択が独自で、実装可能性が高い。今後マルチエージェント系の正しさを論じる際の**理論的座標軸**として頻繁に参照される可能性。

### 7.3 再帰的最適化

#### [May 2026] "Recursive Agent Optimization" [[paper](https://arxiv.org/abs/2605.06639)] 🔥

- **概要**: 著者 Apurva Gandhi, Satyaki Chakraborty, Xiangjun Wang, Aviral Kumar, Graham Neubig（CMU/著名RL/NLP研究者）。**エージェントが自己にタスクを分割委任して再帰的に生成する強化学習手法**。**分割統治により長コンテキスト・困難問題への一般化**を実現し、**訓練効率の向上、モデルのコンテキスト窓を超えるタスク処理、計算時間削減**を実証。
- **差分・新規性**: 既存の自己最適化研究は**フラットな最適化ループ**だったが、本研究は**再帰的自己委任を学習させる**ことで「**コンテキスト窓を超えるタスク**」を扱えるようにする点が独自。Aviral Kumar(RL)とGraham Neubig(NLP)の組み合わせは強力で、実装の質も期待できる。

### 7.4 失敗帰属の体系化

#### [May 2026] "Beyond Individual Intelligence: Surveying Collaboration, Failure Attribution, and Self-Evolution in LLM-based Multi-Agent Systems" [[paper](https://arxiv.org/abs/2605.14892)] 📖

- **概要**: 著者 Shihao Qi, Jie Ma, Rui Xing, Wei Guo, Xiao Huang 他。LLMマルチエージェントシステムにおいて、**エージェント間・ラウンド間でエラーが伝播し診断困難となる課題**を整理したサーベイ。**基盤能力・協調統合・故障帰属・自己改善の4段階からなる "LIFE" フレームワーク**で研究を体系化する。
- **差分・新規性**: マルチエージェントサーベイは多いが、**failure attribution を主題化**したサーベイは初。`AGENTRX`(2602.02475) や `AgenTracer`(2509.03312) で個別研究はあったが、**LIFE フレームワークによる体系化**は実装者にとって**マルチエージェント系の運用問題の地図**として価値が高い。

### 7.5 状態管理の明示化

#### [May 2026] "Multi-agent Collaboration with State Management (STORM)" [[paper](https://arxiv.org/abs/2605.20563)]

- **概要**: 著者 Mengyang Liu 他。**共有コードベースへの並行編集による競合問題**に対し、**ワークスペース分離ではなくエージェント間の相互作用を仲介し書き込み中に競合を解消するSTORM(STate-ORiented Management)** を提案。**Commit0 で 87.6、PaperBench で 78.2 を達成しgit-worktreeベースラインを大幅に上回る**。
- **差分・新規性**: 重要な経験的発見として、**マルチエージェント協調において明示的な状態管理がワークスペース分離より優れる**ことを示した。これは並列開発の業界ベストプラクティス（worktree分離）と逆の結論で、エージェント設計には独自の最適解があることを示唆。

### 7.6 横断的示唆

実装者向けTips:
1. **オーケストレーション層をベイズ整合的に**: `Position: Bayes-consistent orchestration` の発想を、エージェント間のメッセージ交換でルーチン化。
2. **失敗帰属のLIFEフレームワーク**を運用設計の地図に。
3. **状態管理は明示的に**: `STORM` の知見通り、worktree分離より仲介層の方が良い場合がある。
4. **再帰的最適化は強力だが、Hygiene が必須**: `Recursive Agent Optimization` を採用する際は `Ratchet`([2605.22148](https://arxiv.org/abs/2605.22148))系の衛生レシピと組み合わせる。

## 8. Safety & Governance: 行動評価批判と監視可能性

### 8.1 このジャンルのトレンドと課題感

🔍 Safety 研究は5月、**規範論**（何を安全と呼ぶか）が中心になった。特に `Position: Behavioural Assurance Cannot Verify the Safety Claims Governance Now Demands` は、現行の評価パラダイム自体への根源的疑義を提起する重要論文。

### 8.2 行動評価パラダイムへの批判

#### [May 2026] "Position: Behavioural Assurance Cannot Verify the Safety Claims Governance Now Demands" [[paper](https://arxiv.org/abs/2605.15164)] 🔥

- **概要**: 著者 Pratinav Seth, Vinay Kumar Sankarapu。**行動評価やレッドチーミング等の挙動ベース保証手法は、AIガバナンスが要求する隠れた目的・制御喪失耐性・破滅的能力境界を検証できない**と主張するポジションペーパー。**「監査ギャップ」「脆弱な保証」を形式化**し、**21のガバナンス文書を分析**し、**線形プローブ・活性化パッチング等のメカニスティックな証拠アプローチへの移行**を提言。
- **差分・新規性**: 現在の AI 安全評価のほぼ全てが入出力ベースの行動評価（red-teaming, benchmarks）に依拠している中、**そのパラダイム全体を疑う**論文。**21文書分析というガバナンス側の現実とのすり合わせ**を行っており、規範論にとどまらない。AI 規制議論（EU AI Act, US Executive Order）の前提を揺るがす可能性のある重要論文。

### 8.3 可観測性の基盤

#### [Jan 2024] "Visibility into AI Agents" [[paper](https://arxiv.org/abs/2401.13138)] 🔥

- **概要**: 著者 Alan Chan, Carson Ezell, Max Kaufmann, Kevin Wei, Lewis Hammond 他（David Krueger等の安全研究界の大物）。2024年1月公開のFAccT '24基礎論文だが、今期のガバナンス議論で再注目されてリストに追加。**エージェント識別子・リアルタイム監視・活動ログ**という3つの可視性向上手段を分析。**中央集権・分散型双方の展開モデルとサプライチェーン参加者**を考慮し、**個人データ保護と権力分配への含意**を議論する。
- **差分・新規性**: 2年経った今でも参照される基礎論文。`Position: Behavioural Assurance...` の議論を補完する **「何を観測すべきか」** の規範枠組みとして機能。

### 8.4 メモリ層での安全強化

#### [May 2026] "SafeHarbor: Hierarchical Memory-Augmented Guardrail for LLM Agent Safety" [[paper](https://arxiv.org/abs/2605.05704)]

- **概要**: 著者 Zhe Liu, Zonghao Ying 他。ツール使用LLMエージェントの脆弱性に対し、**敵対的生成による文脈認識防御ルール**と**階層メモリ機構**、**エントロピーベースの自己進化機構**を備える SafeHarbor を提案。**GPT-4o で良性タスク有用性63.6%、有害要求への拒否率93%超を両立**。
- **差分・新規性**: 既存のガードレール（入出力フィルタ）が**点的な制約**だったのに対し、本研究は**メモリ階層を用いた構造的境界**を提案。**学習不要で動的に防御ルールを適用**する設計が実用上重要。`SSGM`(2603.11768) のメモリガバナンスを安全側に発展させたもの。

### 8.5 ツール出力の不信前提

#### [May 2026] "Trust No Tool: Evaluating and Defending LLM Agents under Untrusted Tool Feedback" [[paper](https://arxiv.org/abs/2605.17453)]

- **概要**: 著者 Lecheng Yan 他。**初期は信頼できるように振る舞い特定条件で有害化する隠れトリガー型ツール脅威**に対し、**1,970シナリオの TRUST-Bench と非対称評価指標 GuardedJoint** を提案。**多段ツール相互作用を信頼形成パターンの構造化変数に変換するVISTA-Guard** を導入し、**84.2% のドメイン内精度**を達成。
- **差分・新規性**: 既存のエージェントはツール出力を所与のものとして扱うことが多かったが、本研究は **「ツール出力 = 信頼できない外部入力」かつ「信頼は時間とともに形成・破壊される動的変数」** という前提を持ち込む。`SkillScope`([2605.05868](https://arxiv.org/abs/2605.05868)) の最小権限と組み合わせると、**信頼性が階層化されたエージェントアーキテクチャ**が見える。

### 8.6 横断的示唆

実装者向けTips:
1. **行動評価だけに依存しない**: `Position: Behavioural Assurance...` の警告通り、メカニスティック解釈性(線形プローブ・活性化パッチング)を併用。
2. **ハーネスレベルの監査**を独立した layer として実装（`Auditing Agent Harness Safety`[2605.14271](https://arxiv.org/abs/2605.14271)）。
3. **ツール信頼を動的変数として扱う**: `Trust No Tool` のVISTA-Guard発想で、信頼形成パターンを構造化変数化。
4. **可観測性は事後ではなく事前設計**: `Visibility into AI Agents` の3層（ID/ログ/通知）を最初から組み込む。

## 9. Evaluation: 実環境ベンチと多階層評価

### 9.1 このジャンルのトレンドと課題感

🔍 Evaluation 研究は2025年に大きく前進した基盤の上で、今期は **(1) 実世界転移**（Wild benchmark）、**(2) 多階層評価の自動化**、**(3) 評価混在問題の解決** の3軸が顕在化。

### 9.2 実世界 long-horizon ベンチ

#### [May 2026] "WildClawBench: A Benchmark for Real-World, Long-Horizon Agent Evaluation" [[paper](https://arxiv.org/abs/2605.10912)] ⚖️

- **概要**: 著者 Shuangrui Ding 他（Shanghai AI Lab 系）。**6カテゴリにわたる60の人手作成バイリンガル・マルチモーダルタスク**からなり、**各タスクは平均約8分・20回超のツール呼び出し**を要する長期エージェント評価ベンチマーク。**再現可能なDockerコンテナ内で実CLIエージェントハーネスを実行**し、**決定論的チェック・環境状態監査・LLM/VLM判定のハイブリッド採点**を採用。**19のフロンティアモデル評価で Claude Opus 4.7 が62.2%で最高**だが、**長期実行ランタイム評価が未解決課題**であることを示した。
- **差分・新規性**: **8分・20ツール呼び出し**という現実的なタスクサイズで、**実CLIエージェントハーネス**を回す点が独自。Claude Opus 4.7 のスコア62.2% は、**フロンティアモデルでもまだ長期タスクは難しい**ことを示す重要な参照値となる。

#### [Apr 2026] "ClawGym: A Scalable Framework for Building Effective Claw Agents" [[paper](https://arxiv.org/abs/2604.26904)]

- **概要**: 著者 Fei Bai 他（Ji-Rong Wen等中国Renmin Uni系）。ファイル・ツール・永続ワークスペース状態を扱う多段ワークフローのエージェント開発を支援するフレームワーク。**13.5KのフィルタリングされたタスクからなるClawGym-SynData、SFT＋並列サンドボックスRLで訓練するClawGym-Agents、200インスタンスのClawGym-Benchの3要素**を提供。
- **差分・新規性**: **データ合成・学習・診断評価を統合**し、Claw型パーソナルエージェント開発の**全ライフサイクル**を支える初のスケーラブル枠組み。

### 9.3 多階層評価の自動化

#### [May 2026] "Agentic CLEAR: Automating Multi-Level Evaluation of LLM Agents" [[paper](https://arxiv.org/abs/2605.22608)]

- **概要**: 著者 Asaf Yehudai, Lilach Eden, Michal Shmueli-Scheuer（IBM Research）。LLMエージェントの動作を自動評価するフレームワーク。**システム・トレース・ノードの3レベル**で詳細な分析を行い、観測層の上に統合される。**4ベンチマーク・7構成・数千回のLLM呼び出し**で**人間アノテーションとの相関とタスク完了率予測能力**を実証。
- **差分・新規性**: 重要な設計選択として、**静的なエラータクソノミーに頼らず動的に多粒度のエージェント動作テキスト洞察を生成**。`CLEAR`(2507.18392) のエージェント版・多階層版で、failure attribution(`Beyond Individual Intelligence`[2605.14892](https://arxiv.org/abs/2605.14892))と組み合わせると、**階層的かつ因果的な失敗分析**が可能になる。

### 9.4 横断的示唆

実装者向けTips:
1. **Live benchmark を必ず併用**: 静的ベンチは汚染リスクが高い。`WildClawBench` の Docker 内 CLI 実行は良いリファレンス。
2. **多階層評価を自動化**: `Agentic CLEAR` のシステム/トレース/ノード3階層を採用。
3. **データ合成・学習・評価を統合**: `ClawGym` のような統合フレームワークで開発サイクルを高速化。
4. **長期タスクは現状フロンティアでも難しい**: WildClawBench で Claude Opus 4.7 が 62.2% という事実を念頭に、ユーザ期待値を調整。

## 10. Harness: モデル外の "OS層" として確立した研究領域

### 10.1 Harness とは何か：3月→5月の研究対象としての成立

🔍 「Agent Harness」という用語は、2026年3月までは曖昧な工学用語にすぎなかった。実行スクリプト、設定ファイル、シェルラッパー等の総称として使われていたが、研究対象として明確に定義されてはいなかった。3月の `AutoHarness`(2603.03329)・`Natural-Language Agent Harnesses`(2603.25723)・`Meta-Harness`(2603.28052) が転機となり、5月には **7本のHarness関連論文**が同時期に出現することで、Harness は **「LLMエージェントの能力を引き出す/制約する、モデル外の実行レイヤ」** として正式に研究対象化した。

今期の Harness 研究は、次の **5つの軸**で同時並行に進展している:

| 軸 | 主要論文 | 中心的主張 |
|---|---|---|
| **(1) 体系化** | `Code as Agent Harness`([2605.18747](https://arxiv.org/abs/2605.18747)) | Harness は「インタフェース・メカニズム・スケーリング」の3層構造 |
| **(2) 適応** | `Life-Harness`([2605.22166](https://arxiv.org/abs/2605.22166)) | モデルではなくハーネスを適応させるべき。1→17モデル転送 |
| **(3) ミニマリズム** | `Is Grep All You Need?`([2605.15184](https://arxiv.org/abs/2605.15184)) | grep + 適切なハーネス > ベクタDB + 複雑RAG |
| **(4) 安全監査** | `HarnessAudit`([2605.14271](https://arxiv.org/abs/2605.14271)) | ハーネス自体が攻撃面。軌跡全体を監査対象に |
| **(5) 進化制御** | `Harnessing Agentic Evolution`([2605.13821](https://arxiv.org/abs/2605.13821)) | ハーネスを進化の制御層として再定義 |

加えて、`HeavySkill`([2605.02396](https://arxiv.org/abs/2605.02396))のタイトル「Heavy Thinking as the **Inner Skill in Agentic Harness**」、`PriorZero`([2605.12289](https://arxiv.org/abs/2605.12289))の世界モデル統合、Cybersecurity の `Cochise`([2605.11671](https://arxiv.org/abs/2605.11671)) の参照ハーネス公開など、**他分野の論文も Harness をキーワードとして共有**するようになっており、横断的な共通言語となりつつある。

残課題: **Harness の標準化**（OCI Registry/MCP Registry 的なエコシステム）、**Harness 進化の安全性保証**、**Harness と Skill の境界線**。

### 10.2 体系化: Code as Agent Harness（42名共著の決定版サーベイ）

#### [May 2026] "Code as Agent Harness" [[paper](https://arxiv.org/abs/2605.18747)]

- **概要**: 著者 Xuying Ning, Katherine Tieu, Dongqi Fu, Tianxin Wei, Zihao Li 他**42名**（UIUCの Jingrui He グループを核に、Adobe・MITほか多数の研究機関が参加）。**コードがAIエージェントのインフラとして果たす役割を整理**したサーベイで、**3層構造**で分析する:
  1. **インタフェース層**: エージェントが環境を観測・操作する境界の設計
  2. **メカニズム層**: 計画・記憶・推論を支える内部機構
  3. **スケーリング層**: マルチエージェント協調・分散実行
- 応用範囲として **コーディング支援、GUI操作、ロボット、科学研究、エンタープライズシステム**を網羅する。
- **差分・新規性**: コードを **「単なるエージェントの出力対象」ではなく「推論・意思決定・検証を支えるハーネス」** として捉え直す統一的フレームワーク。42名という著者数は、コミュニティが **Harness を一つの研究分野として認識し始めた**ことを象徴する。Skillsの `A Comprehensive Survey on Agent Skills`([2605.07358](https://arxiv.org/abs/2605.07358)) と並んで、**エージェント周辺の工学化**を推進する重要論文。
- **位置付け**: 本サーベイの3層構造は、今後 Harness 研究の標準的な分類枠組みになる可能性が高い。特に **「インタフェース層」を独立の研究対象として定義**したことは、後述する `Life-Harness` の "Adapt Interface, Not Model" 主張の理論的土台となる。

### 10.3 適応: Adapt Interface, Not Model のパラダイム転換

#### [May 2026] "Adapting the Interface, Not the Model: Runtime Harness Adaptation for Deterministic LLM Agents (Life-Harness)" [[paper](https://arxiv.org/abs/2605.22166)]

- **概要**: 著者 Tianshi Xu, Huifeng Wen, Meng Li。**モデルパラメータではなく実行時インタフェースを変更**して凍結LLMエージェントを強化する **Life-Harness** を提案。タイトル "Adapting the Interface, Not the Model" 自体が中心的主張で、ファインチューニングやRLHFといったモデル側の介入を行わずに性能を改善する道を示す。
- **対象とする4種類の失敗**:
  1. **環境契約（environment contracts）の違反**: APIの暗黙的前提条件をエージェントが守らない
  2. **手続きスキル（procedural skills）の欠如**: タスクに必要な定型手順を実行できない
  3. **行動実現（action realization）の不確実性**: 意図された行動が環境に正しく反映されない
  4. **軌跡規制（trajectory regulation）の失敗**: 長期実行で軌道が逸脱する
- これらすべてを**再利用可能なハーネス介入**に変換する。
- **実証結果**: **7環境18モデルで126設定中116設定を改善**、**平均88.5%の相対改善**。最も重要な発見は **「1モデルの軌跡から作ったハーネスが17モデルへ転送可能」** であること。これは、ハーネスが捉えているのは **モデル固有の弱点ではなく環境固有のパターン**であることを示す決定的証拠。
- **差分・新規性**: 「**多くの性能問題はモデルではなくハーネス設計に起因する**」という主張を **1モデル→17モデル転送可能** という驚くべき経験的結果で実証する。これは、業界の慣行（「性能が足りなければファインチューニング/モデル変更」）への根本的挑戦。**ハーネス側に投資する経済合理性**を示した点で、今後の実装パイプライン設計に大きな影響を与える可能性がある。
- **`HeavySkill`([2605.02396](https://arxiv.org/abs/2605.02396))との関係**: `HeavySkill` が「外部オーケストレーションではなく LLM 内部の推論能力（inner skill）を強化」と主張するのに対し、`Life-Harness` は逆に「**モデル外の介入で性能を引き上げる**」と主張する。両者は対立しているのではなく、**inner skill（モデル内部）と outer harness（モデル外部）の両方が改善余地**であることを示しており、設計者は両軸を比較検討する必要がある。

### 10.4 ミニマリズム: Is Grep All You Need? の業界常識への挑戦

#### [May 2026] "Is Grep All You Need? How Agent Harnesses Reshape Agentic Search" [[paper](https://arxiv.org/abs/2605.15184)] 🔥

- **概要**: 著者 Sahil Sen, Akhil Kasturi, Elias Lumer, Anmol Gulati, Vamse Kumar Subbiah。エージェントワークフローにおける検索戦略とエージェント設計の相互作用を体系的に分析。**Chronos/Claude Code/Codex/Gemini CLI** という主要な現代エージェントハーネスを用いて、**116問の grep vs ベクター検索**を比較。**無関係な会話履歴を追加した性能劣化実験**も実施。
- **主要発見**:
  - **grep検索が概してベクター検索を上回る**。
  - ただし**性能はハーネスとツール呼び出しパラダイムに強く依存**する。同じツールでも、ハーネスが変わると結果が変わる。
  - 無関係履歴の挿入はベクター検索よりgrepの方が頑健である傾向。
- **差分・新規性**: これは「**RAGはまずベクタDB**」「**埋め込みベース検索が最先端**」という業界常識への直接的挑戦。`Code as Agent Harness`([2605.18747](https://arxiv.org/abs/2605.18747)) の **コードベースのシンプルなハーネス**思想と整合し、**過剰な抽象化を避けるミニマリズム潮流**の代表例となる。多くの実装者にとって、**Vector DB + 埋め込みモデル + リランカー** という三重投資の正当性を問い直す材料になる。
- **実装上の含意**: コードベース検索系の RAG パイプライン（Cursor, Claude Code, Codex の内部実装）が、より単純な grep ベースに回帰する可能性。少なくとも、**新規プロジェクトでベクタ DB を即座に採用する判断は再考すべき**。
- **Deep Research セクションとの呼応**: 同じく多段階処理の単一化を提案する `SIRA`([2605.06647](https://arxiv.org/abs/2605.06647)) と思想を共有する。両者は、**「複雑さは正義ではない」** という共通メッセージを発している。

### 10.5 安全監査: HarnessAudit による軌跡全体の検証

#### [May 2026] "Auditing Agent Harness Safety (HarnessAudit)" [[paper](https://arxiv.org/abs/2605.14271)] ⚖️

- **概要**: 著者 Chengzhi Liu, Yichen Guo, Yepeng Liu, Yuzhe Yang, Qianqi Yan, Xuandong Zhao, Wenyue Hua, Sheng Liu, **Sharon Li**(UW-Madison, OOD検出の著名研究者), Yuheng Bu, **Xin Eric Wang**(UCSC) という安全性研究の大物を含むグループによる研究。**エージェントのハーネス（実行フレームワーク）安全性を監査する HarnessAudit** を提案。
- **監査の3軸**:
  1. **境界遵守（boundary compliance）**: ハーネスが定めた行動境界をエージェントが守っているか
  2. **実行忠実性（execution fidelity）**: 意図された手順が正しく実行されているか
  3. **システム安定性（system stability）**: 長期実行でシステム全体が安定しているか
- **HarnessAudit-Bench**: **8ドメインに渡る210タスク**で**10構成**を評価。**重要な経験的発見**として、**違反は実行中に発生し、トラジェクトリ長と共に増加する**ことを確認。これは「最終出力だけ見ればいい」という従来の安全評価の致命的盲点を示す。
- **差分・新規性**: 既存の安全評価は**モデルやプロンプト中心**だったが、本研究は **「ハーネスも安全性の重要構成要素」** という認識を示す。**最終出力ではなく実行軌跡全体を対象**とした**初のハーネス安全性監査フレームワーク**で、Safety セクションの `Position: Behavioural Assurance...`([2605.15164](https://arxiv.org/abs/2605.15164)) の**構造的監査**の流れを、ハーネスレベルで具現化したもの。
- **Skills セクションの `SkillScope`([2605.05868](https://arxiv.org/abs/2605.05868)) との関係**: `SkillScope` がスキル単位の最小権限を扱うのに対し、`HarnessAudit` はハーネス全体の境界遵守を扱う。両者は **多層防御（defense in depth）** として組み合わせ可能で、**(a) ハーネスが大枠を定義** → **(b) スキルが個別権限を細粒度で制御** → **(c) Counterfactual Trace Auditing が事後監査** という運用パイプラインが構築できる。

### 10.6 進化制御: ハーネスを進化の対話環境として再定義

#### [May 2026] "Harnessing Agentic Evolution (AEvo)" [[paper](https://arxiv.org/abs/2605.13821)]

- **概要**: 著者 Jiayi Zhang, Yongfeng Gu, Jianhao Ruan, Maojia Song 他（**Chenglin Wu** はMetaGPTの主要著者、**Yuyu Luo** は HKUST）。**エージェント進化を対話環境（dialogue environment）として扱い**、累積進化コンテキストをプロセスレベルの状態として用いるAEvo を提案。
- **重要な設計選択**: メタエージェントが **候補を直接提案するのではなく、手順やエージェントコンテキストを編集する**。これは「進化」を **「コンテキスト編集の連続」** として抽象化することで、強化学習や対話学習の枠組みで進化を扱えるようにする。
- **実証結果**: **最強ベースラインに対し26%の相対改善**、3つのオープンエンド最適化タスクで SOTA。**手順型（procedural）・エージェント型（agentic）双方の手法に対応**する一般性を持つ。
- **差分・新規性**: 既存の自己進化研究はエージェント内部の機構変更が中心だったが、本研究は **ハーネス層から進化を制御**するアプローチ。Self-Evolution の `Ratchet`([2605.22148](https://arxiv.org/abs/2605.22148)) が「進化の衛生（hygiene）」を提案したのに対し、AEvo は「**進化の抽象化フォーマット**」を提案する。両者を組み合わせると、**(a) AEvo が進化を対話として実行** → **(b) Ratchet が衛生を保証** という多層構造になる。
- **Harness 文脈での意義**: 「**ハーネスを進化の場として使う**」という発想は新しく、**ハーネスが単なる実行基盤ではなく、エージェント能力の継続的改善層**でもあることを示している。

### 10.7 世界モデルとの統合: PriorZero

#### [May 2026] "PriorZero: Bridging Language Priors and World Models for Decision Making" [[paper](https://arxiv.org/abs/2605.12289)]

- **概要**: 著者 Junyu Xiong, Yuan Pu, Jia Tang, Yazhe Niu。LLMの世界知識と強化学習エージェントを統合する手法。**(1) MCTSルートでLLM事前分布を注入して探索を誘導**、**(2) 世界モデル改善とLLM適応を分離**、**(3) 価値推定でLLMを安定微調整**。**Jericho と BabyAI で探索効率と性能を改善**。
- **差分・新規性**: 世界モデル研究（DreamerV3系）と LLM エージェント研究はやや分断していたが、本研究は両者を **事前知識（LLM側）と環境モデル（世界モデル側）の補完関係** として統合する。**LightZero フレームワークの拡張**として実装されている点も実用上重要で、既存のRLパイプラインに組み込みやすい。
- **Harness 文脈での位置付け**: LLM を **世界モデルの探索を誘導する prior** として扱うこの設計は、**「LLM がハーネスの一部として MCTS をガイドする」** という新しい役割を提示する。これは `Code as Agent Harness` の 3層構造で言えば、**メカニズム層に LLM 事前分布を組み込む**設計パターン。

### 10.8 横断: 他分野の論文に現れる Harness

Harness は他セクションの論文でもキーワードとして頻出する:

| 論文 | Harness 文脈での役割 |
|---|---|
| **HeavySkill** ([2605.02396](https://arxiv.org/abs/2605.02396)) | "Heavy Thinking as the Inner Skill in **Agentic Harness**" ── 推論をハーネス内部のスキルとして位置付け |
| **Cochise** ([2605.11671](https://arxiv.org/abs/2605.11671)) | 自律ペンテスト向けの **597行 Python 参照ハーネス**を公開。Cybersecurity 研究の事実上のベースライン |
| **ClawGym** ([2604.26904](https://arxiv.org/abs/2604.26904)) | データ合成・学習・診断評価を統合したエージェント開発ハーネス |
| **WildClawBench** ([2605.10912](https://arxiv.org/abs/2605.10912)) | **再現可能な Docker コンテナ内で実 CLI エージェントハーネスを実行** |

これは、Harness が **エージェント研究全体の共通言語**として定着しつつあることを示している。

### 10.9 Harness と Skill の境界線

Harness と Skill は混同されがちだが、本号の論文群から区別が明確化しつつある:

| 軸 | Harness | Skill |
|---|---|---|
| **抽象度** | 実行基盤（OS的） | 再利用可能な手順（パッケージ的） |
| **粒度** | エージェント全体に作用 | 特定タスクに紐づく |
| **適応単位** | 環境/ドメイン | タスク種別 |
| **代表論文** | `Code as Agent Harness`, `Life-Harness` | `A Comprehensive Survey on Agent Skills`, `SkillsVote` |
| **安全機構** | `HarnessAudit`（軌跡全体） | `SkillScope`（細粒度権限） |
| **進化** | `Harnessing Agentic Evolution`（コンテキスト編集） | `SkillFlow`/`SkillOS`（個別スキルの作成・退役） |

実装的には、**Harness が骨格を決め、Skill がその上で動く能力単位**と理解するのが整理しやすい。両者は階層関係にあり、競合ではなく**補完関係**にある。

### 10.10 ハーネス設計のアンチパターン（今期の論文から）

今期の Harness 研究から、**やってはいけない設計**が浮かび上がる:

1. **❌ ベクタDB を最初から使う**（`Is Grep All You Need?` の知見）
   → grep + 適切なハーネスで十分な場合が多い。投資コストの正当化が必要。
2. **❌ モデル変更で性能問題を解決しようとする**（`Life-Harness` の知見）
   → 多くの場合、ハーネス側に問題がある。1モデル→17モデル転送可能なハーネス介入が存在する。
3. **❌ 最終出力のみで安全性を評価する**（`HarnessAudit` の知見）
   → 違反は実行中に発生し、軌跡長とともに増加する。軌跡全体の監査が必須。
4. **❌ ハーネスを設定ファイル/ad-hocスクリプトで管理する**（`Code as Agent Harness` の示唆）
   → ハーネスは**コードとしてバージョン管理・テスト・レビュー可能**な状態に。
5. **❌ ハーネスを静的な実行基盤と見なす**（`AEvo` の示唆）
   → ハーネスは**進化の場でもある**。コンテキスト編集による継続改善を組み込むべき。

### 10.11 横断的示唆と実装Tips（保存版）

**設計判断のチェックリスト**:

1. **モデル変更の前にハーネス見直し**
   - `Life-Harness` の **1モデル→17モデル転送可能** という発見は、ハーネス側に投資する根拠。
   - チェック: ファインチューニング前に、ハーネスの環境契約・手続きスキル・行動実現・軌跡規制の4軸を見直したか？

2. **既存のシンプルなツールを再評価**
   - `Is Grep All You Need?` の知見で、ベクタDBより grep の方が良い場合がある。
   - チェック: Vector DB + 埋め込みモデル + リランカーの三重投資の正当性は検証済みか？

3. **ハーネスをコードとして管理**
   - バージョン管理、テスト、レビューの対象に（`Code as Agent Harness` サーベイの示唆）。
   - チェック: ハーネスは git 管理されているか？ ユニットテストはあるか？ レビュープロセスはあるか？

4. **ハーネス安全性も独立に監査**
   - `HarnessAudit` の3軸（境界遵守・実行忠実性・システム安定性）。
   - チェック: 最終出力だけでなく、軌跡全体を監査しているか？ トラジェクトリ長で違反が増えていないか？

5. **ハーネスを進化の場として活用**
   - `AEvo` のコンテキスト編集による進化を組み込む。
   - チェック: ハーネスは**静的設定**で固定されていないか？ 経験から継続改善されているか？

6. **Harness と Skill の役割を分離**
   - ハーネスは骨格、スキルは能力単位。
   - チェック: 同じ機能をハーネスとスキルの両方で実装していないか？

7. **多層防御の構築**
   - ハーネス境界（HarnessAudit）＋ スキル権限（SkillScope）＋ トレース監査（Counterfactual Trace Auditing）の3層。
   - チェック: 単一層に依存していないか？

**運用時の指標**:

- **Harness Conformance Rate**: 境界遵守率（`HarnessAudit` 由来）
- **Trajectory Length vs Violation Rate**: 長期実行での違反増加曲線
- **Interface Transfer Score**: あるモデルで作ったハーネスが他モデルでも動くか（`Life-Harness` 由来）
- **Search Tool Effectiveness**: grep vs vector の相対性能（`Is Grep All You Need?` 由来）

## 11. Research Agents: 「AI Scientist」への懐疑

### 11.1 このジャンルのトレンドと課題感

🔍 Research Agents（科学エージェント）分野は2024年の `The AI Scientist`(2408.06292) 以来、急速に拡大した。今期は**懐疑的論調**が顕在化し、「**完全自動の科学者**」幻想からの脱却が進んでいる。

### 11.2 科学エージェント懐疑論の決定版

#### [May 2026] "Agentic AI Scientists Are Not Built For Autonomous Scientific Discovery" [[paper](https://arxiv.org/abs/2605.08956)] 🔥

- **概要**: 著者 Harshit Bisht, Vinay Kumar, Kevin Maik Jablonka, Mausam, N. M. Anoop Krishnan（インドIIT系 + Jablonka材料化学AI 等）。**AIサイエンティストは協働者として機能するが自律的発見には未到達**と主張。**4つの障壁**を指摘:
  1. **McNamara誤謬**（測定可能なものに偏重）
  2. **暗黙知の欠如**
  3. **ポストトレーニングによる多様性低下**
  4. **単一ターン精度に偏ったベンチマーク**
- **差分・新規性**: `AI Scientists Fail Without Strong Implementation Capability`(2506.01372) の流れを汲む懐疑論の決定版。**スケーリングではなく再設計が必要**として、**科学シミュレーション検証、永続世界モデル、AI仮説プレレジストリ、必要駆動の応用**を提案。これらの提言は今後の研究エージェント設計の方向性を変える可能性が高い。

### 11.3 AIレビュアーの大規模実証

#### [May 2026] "On the limits and opportunities of AI reviewers: Reviewing the reviews of Nature-family papers with 45 expert scientists" [[paper](https://arxiv.org/abs/2605.20668)] 🔥

- **概要**: 著者 Seungone Kim, Dongkeun Yoon, Kiril Gashteovski 他**計58名**（KAIST/CMU等の連合）。**45名の科学者が469時間かけNature論文82本に対する人間/AIレビューの2,960指摘を、正確性・重要性・根拠面で評価**。重要な経験的結論: **GPT-5.2は上位人間レビュアーに匹敵（60.0% vs 48.2%）し、約1/4のケースで人間が見落とした問題を発見**。
- **差分・新規性**: 既存の AI レビュアー研究が小規模・限定的だったのに対し、本研究は**Nature 系・45名科学者・469時間**という規模で、AIレビュアーの**実用限界**を厳密に測定。**AIレビュアーは過剰な重複・狭い専門知識・長文文書管理に課題があるが、人間補助としては有用**との実証的結論は、今後の peer review 議論の基本文献となる。

#### [Apr 2026] "Can AI Be a Good Peer Reviewer? A Survey of Peer Review Process, Evaluation, and the Future" [[paper](https://arxiv.org/abs/2604.27924)] 📖

- **概要**: 著者 Sihong Wu 他（Arman Cohan等の著名NLP研究者）。LLMによる査読支援/代替を体系的に整理したサーベイ。**レビュー生成手法(SFT、エージェント、RL)・反論/メタレビュー/改稿生成・人間/LLMベース評価の3軸**を扱い、**データセット、倫理、限界、今後の発展**を議論。
- **差分・新規性**: AI レビューに特化したサーベイは初。`On the limits and opportunities of AI reviewers`([2605.20668](https://arxiv.org/abs/2605.20668)) の実証研究と相補的な、**概念整理側**の研究。

### 11.4 パーソナライズ研究エージェント

#### [May 2026] "NanoResearch: Co-Evolving Skills, Memory, and Policy for Personalized Research Automation" [[paper](https://arxiv.org/abs/2605.10813)]

- **概要**: 著者 Jinhang Xu 他。パーソナライズ研究自動化のためのマルチエージェント枠組み。**(1) スキルバンク(再利用可能な手続き規則)、(2) ユーザ固有メモリ、(3) フィードバックを永続パラメータ更新に変換するポリシー学習**が共進化。
- **差分・新規性**: 既存の研究エージェントは「**汎用的な科学者**」を目指していたが、本研究は **「特定研究者の研究を支援する小さなエージェント」** を提案。これは AI Scientist 懐疑論（`Agentic AI Scientists Are Not Built`[2605.08956](https://arxiv.org/abs/2605.08956)）への現実的応答とも読める。`Towards Self-Evolving Agentic Literature Retrieval (PaSaMaster)`([2605.14306](https://arxiv.org/abs/2605.14306)) と組み合わせると、**個別研究者の長期パートナー**像が見える。

### 11.5 横断的示唆

実装者向けTips:
1. **完全自動化を目指さない**: `Agentic AI Scientists Are Not Built` の4障壁（McNamara誤謬、暗黙知欠如、多様性低下、単一ターン偏重）を踏まえた設計に。
2. **人間レビューを構造的に組み込む**: AIレビュアーは**1/4のケースで人間が見落とした問題を発見**する補助役として有効。
3. **パーソナライズを重視**: `NanoResearch` の発想で、特定ユーザ/分野に特化したエージェント。

## 12. Enterprise / Data / Finance: ガバナンスとスプレッドシート

### 12.1 このジャンルのトレンドと課題感

🔍 エンタープライズ採用フェーズでは、技術的能力よりも **(1) ガバナンス**、**(2) レガシー統合**、**(3) ドメイン固有の摩擦**（スプレッドシート、Excel ベースの業務等）が決定的な障壁となる。今期はこれらに正面から向き合う論文が増えている。

### 12.2 設計時ガバナンス

#### [May 2026] "Governance by Construction for Generalist Agents (CUGA)" [[paper](https://arxiv.org/abs/2605.20874)]

- **概要**: 著者 Segev Shlomov 他（IBM Researchグループ）。エンタープライズエージェントのコンプライアンス強制のための **CUGA ポリシーシステム**。**Intent Guard・Playbook・Tool Guide・Tool Approvals・Output Formatterの5チェックポイント**でルールを実行時に強制し、**モデル微調整不要**。
- **差分・新規性**: 既存のガバナンス研究は**運用時の監視・監査**が中心だったが、本研究は**設計時の構造的組み込み**を提案。**監査可能で予測可能なエージェント動作**を実現する構築時ガバナンス枠組みで、**医療事例で実証**されている点が実用上重要。Safety の `Position: Behavioural Assurance...`([2605.15164](https://arxiv.org/abs/2605.15164)) と思想を共有。

### 12.3 レガシーシステムの近代化

#### [May 2026] "Reversa: A Reverse Documentation Engineering Framework for Converting Legacy Software into Operational Specifications for AI Agents" [[paper](https://arxiv.org/abs/2605.18684)]

- **概要**: 著者 Sanderson Oliveira de Macedo, Ronaldo Martins da Costa。レガシーシステムをAIコーディングエージェント向けの**機械可読仕様**へ逆生成するパイプライン。**複数の専門エージェントがマッピング、モジュール解析、隠れたルール抽出、設計、仕様生成、検証を逐次実行**。**COBOL→Go の ATMケース**で**500件以上のクレームを生成**。
- **差分・新規性**: 既存のレガシー近代化は**コード変換**が中心だったが、本研究は**仕様抽出**を主題化。AI エージェント時代における新しい近代化の意味で、**「エージェントが扱えるドキュメント形式」** という新しい工学要件を提示。**COBOL→Goの実例 + 500件超のクレーム生成**は実用度の高い実証。

### 12.4 時系列・データ分析

#### [May 2026] "Detecting Time Series Anomalies Like an Expert (SAGE)" [[paper](https://arxiv.org/abs/2605.05725)]

- **概要**: 著者 Hyeongwon Kang 他。時系列異常検知のマルチエージェント枠組み**SAGE**。**点・構造・季節性・パターン異常それぞれを担当する専門エージェント、それらをまとめるDetector、診断要約を作るSupervisor**で構成。**ラベル無しで正常データから合成例を生成**。**3つのベンチマークで既存ML/LLM手法を上回り、信頼性と実用性を実証**。
- **差分・新規性**: 既存の時系列異常検知は単一モデルベースが多かったが、本研究は**専門家の分業構造**を模倣。**ラベル無し設定**で動く点が産業実用上重要。`Nexus`([2605.14389](https://arxiv.org/abs/2605.14389)) と並んで、**金融・運用分析の Multi-Agent 化**潮流。

#### [May 2026] "Nexus: An Agentic Framework for Time Series Forecasting" [[paper](https://arxiv.org/abs/2605.14389)] 🔥

- **概要**: 著者 Sarkar Snigdha Sarathi Das, Palash Goyal, Mihir Parmar, Nanyun Peng, Vishy Tirumalashetty, Chun-Liang Li, Rui Zhang, Jinsung Yoon, **Tomas Pfister**（Google Cloud AI Research）。**時系列予測を数値外挿だけでなくニュース等の文脈情報の推論を要する課題と捉え**、**専門段階に分解して時間変動を異なるスケールで分離しコンテキストを統合**するNexusを提案。**不動産・株式など訓練カットオフ後データで検証**。
- **差分・新規性**: Google Cloud AI Research のフラッグシップ的研究で、商用化を視野に入れた重量級論文。**数値+文脈推論を構造化**することでLLMの予測能力を引き出し、**解釈可能な予測根拠**を生成。`Detecting Time Series Anomalies Like an Expert (SAGE)`([2605.05725](https://arxiv.org/abs/2605.05725)) と相補的で、時系列分野におけるエージェント化を牽引。

### 12.5 スプレッドシート操作

#### [May 2026] "WorkstreamBench: Evaluating LLM Agents on End-to-End Spreadsheet Tasks in Finance" [[paper](https://arxiv.org/abs/2605.22664)] ⚖️

- **概要**: 著者 Thomson Yen 他（Hongseok Namkoong含むColumbia系）。**金融ワークフローでスプレッドシートをゼロから作成するエンドツーエンドのエージェント評価ベンチマーク**。**Accuracy/Formula/Format の3軸タクソノミー**で**可読性・修正可能性も評価**。**Claudeが最強だが、複雑度が増すと急落**することを示す。
- **差分・新規性**: 既存QA型ベンチを超え、**プロ品質スプレッドシート作成能力**を評価する初の試み。「**ゼロから作成**」という設定が現実的で、**評価軸が3階層**(Accuracy/Formula/Format)に分解されている点も実用上重要。

#### [May 2026] "Spreadsheet-RL: Advancing Large Language Model Agents on Realistic Spreadsheet Tasks via Reinforcement Learning" [[paper](https://arxiv.org/abs/2605.22642)]

- **概要**: 著者 Banghao Chi 他（Klara Nahrstedt含むイリノイ大系）。**Excel自動化向けLLMエージェントを強化するRL枠組み**。**オンラインフォーラムからの自動データ収集パイプライン**と、**金融・サプライチェーンを含む Domain-Spreadsheet ベンチ**を構築。**Excel機能とツール、ルーティングルールを露出するサンドボックス**を提供。**SpreadsheetBench で 12.0→23.4%、独自データで 8.4→17.2% へ Pass@1 を改善**。
- **差分・新規性**: スプレッドシート操作は**離散的・長期的・連鎖的**であり、RL の適用が難しかったが、本研究はその課題に取り組む。**12→23.4% という大きな改善**を達成。`SheetMind`(2506.12339) などの流れの先で、RLによる本格的な性能向上を示した。

### 12.6 エンタープライズ分析

#### [May 2026] "Beyond Text-to-SQL: An Agentic LLM System for Governed Enterprise Analytics APIs" [[paper](https://arxiv.org/abs/2605.21027)]

- **概要**: 著者 Gundeep Singh 他。**生のDBアクセスではなくエンタープライズ分析APIへの安全な対話**に自然言語意図を変換する**Analytic Agent**を提案。**一貫性・監査可能性・セキュリティを保証**。**90件の実エンタープライズユースケース**で**権限検証・統制クエリ実行・準拠可視化**を多段推論で実現。
- **差分・新規性**: 既存の Text-to-SQL は**個別クエリ生成**が中心だったが、本研究は**ガバナンスが組み込まれた API 層**を介する。**90件の実ユースケース**での検証は、実用度の高さを示す。`AgenticRAG`([2605.05538](https://arxiv.org/abs/2605.05538)) と並んで、エンタープライズ採用の**現実的要件**を主題化。

#### [May 2026] "Building AI Companions that Prioritise Learning over Performance" [[paper](https://arxiv.org/abs/2605.04816)]

- **概要**: 著者 Hassan Khosravi, Dragan Gasevic, Shazia Sadiq 他（教育工学界の著名研究者多数）。教育AIにおける**パフォーマンス向上と学習成果のテンション(摩擦)**を扱う。**教育設計、適応性、責任ある設計の3本柱**で「適応的・教育学的LLMエージェント」を提案。**5つの教育事例**でツールの現状と限界を示す。
- **差分・新規性**: 既存のエージェント研究は性能向上が主目的だったが、本研究は **「ユーザ学習を阻害しないエージェント」** という新しい設計目標を提示。**持続的理解、メタ認知、学習者自律性を優先する設計原理**は、教育以外のスキルアップ系企業エージェントにも応用可能。

### 12.7 探索的データ分析

#### [May 2026] "DataClawBench: An Agent Benchmark for Exploratory Real-World Financial Data Analysis" [[paper](https://arxiv.org/abs/2605.02503)] ⚖️

- **概要**: 著者 Qiaohong Zhang 他（Sun Yat-sen大グループ）。**約206万件の実データを含む探索的金融データ分析エージェントベンチ**。**企業・産業・政策の3領域、欠損などの実欠陥を残し、492の横断タスクに中間チェックポイントを付与**。**8つの先進LLMを評価**。
- **差分・新規性**: 重要な経験的発見として、**探索的データ分析がエージェントの信頼性を破壊する**ことと、**探索量増加が改善に必ずしも繋がらない**ことを実証。これは「**探索すればするほど良い**」という安易な信念への警鐘。

### 12.8 横断的示唆

実装者向けTips:
1. **ガバナンスを設計時に組み込む**: `CUGA` の5チェックポイント(Intent Guard/Playbook/Tool Guide/Tool Approvals/Output Formatter)を参考に。
2. **レガシーシステムからの仕様抽出**を AI ワークフローの最初のステップに（`Reversa` の発想、COBOL→Go実例）。
3. **時系列・データ分析はマルチエージェント設計を検討**: `Nexus` や `SAGE` の発想。
4. **スプレッドシート操作の能力を独立評価**: `WorkstreamBench` の Accuracy/Formula/Format 3軸で自社モデルを測る。
5. **Text-to-SQL は出発点であって到達点ではない**: `Beyond Text-to-SQL` の発想で、API 層・ガバナンス層を分離設計。
6. **「探索すればするほど良い」は誤り**: `DataClawBench` の知見で、探索量増加が逆効果になる場合がある。

## 13. Capability Papers 横断: Knowledge, Learning, Reasoning, Planning

### 13.1 Knowledge

#### [May 2026] "PEEK: Context Map as an Orientation Cache for Long-Context LLM Agents" [[paper](https://arxiv.org/abs/2605.19932)]

- **概要**: 著者 Zhuohan Gu, Qizheng Zhang, **Omar Khattab**（ColBERT/DSPyの著者）, **Samuel Madden**（MIT）。**反復される外部コンテキスト(文書集合、コードリポジトリ)に対する「方向付け知識」を保持**する PEEK。**Distiller・Cartographer・Evictor の3要素**で**固定トークン予算の編集可能キャッシュ**を構成。**ベースラインに対し6.3-34.0%改善**し、**反復回数とコストを削減**。複数LLM/エージェント構成で一貫した利得。
- **差分・新規性**: 長コンテキスト研究は**注意機構の改善**が中心だったが、本研究は**コンテキスト構造の補助インデックス**という新しい層を提示。**Omar Khattab(ColBERT/DSPy)が著者**であることから、IR/RAG コミュニティでの注目度が高い実装になる可能性。

### 13.2 Learning

#### [May 2026] "Generate, Filter, Control, Replay: A Comprehensive Survey of Rollout Strategies for LLM Reinforcement Learning (GFCR)" [[paper](https://arxiv.org/abs/2605.02913)] 📖

- **概要**: 著者 Rohan Surana 他**計27名**の大規模共著。**LLMのRL後訓練におけるロールアウトパイプラインを Generate/Filter/Control/Replay の4段階に分解する GFCR 枠組み**を提案。**検証可能報酬、プロセス監視、ジャッジゲート、ツリーロールアウト**を統合し、**数学、コード/SQL、マルチモーダル、エージェント**の事例で診断を提供。
- **差分・新規性**: LLM RL の急速な発展の中で、**ロールアウト戦略に特化したサーベイは初**。実装者にとって**設計選択のガイドライン**として価値が高い。

#### [May 2026] "On Training Large Language Models for Long-Horizon Tasks: An Empirical Study of Horizon Length" [[paper](https://arxiv.org/abs/2605.02572)]

- **概要**: 著者 Sunghwan Kim 他（Furu Wei含むMicrosoft+延世大グループ）。**同一決定論理で行動長のみが異なる制御実験**を構築し、**長期軌跡が訓練の不安定性・探索・信用割当を悪化させる**ことを示す。重要な処方箋: **ホライズン短縮が訓練を安定化し、短縮ホライズンで訓練したモデルが長尺へ転送可能（horizon generalization）**。
- **差分・新規性**: 長期タスク訓練困難の原因を**ホライズン長として切り出し、horizon reductionによる解決**を提案する empirical study。これは長期タスク訓練の業界ベストプラクティスを変える可能性のある実用的知見。

#### [May 2026] "Learning Agentic Policy from Action Guidance (ActGuide-RL)" [[paper](https://arxiv.org/abs/2605.12004)]

- **概要**: 著者 Yuxiang Ji 他。**高コストなSFTに頼らず、日常的な人間インタラクションデータを行動ガイダンスとして用いる**ActGuide-RL。**混合方策訓練でロールアウトと併せて最適化**し、**タスク難度に応じた適応的フォールバック機構でオフポリシーリスクを抑制**。**Qwen3-4BでGAIA +10.7pp、XBench +19ppを達成しSFT+RL同等性能をコールドスタートデータなしで実現**。
- **差分・新規性**: 既存のエージェント学習は**報酬ベースか模倣ベース**が中心だったが、本研究は**ガイダンス**という中間表現を活用。**コールドスタートデータなしで SFT+RL 同等**を達成した点が実用上極めて重要。

### 13.3 Reasoning

#### [May 2026] "Tools as Continuous Flow for Evolving Agentic Reasoning (FlowAgent)" [[paper](https://arxiv.org/abs/2605.07339)]

- **概要**: 著者 Tairan Huang 他。**ツール連鎖を意味空間内の連続軌跡生成として再定義**するFlowAgent。**条件付きフローマッチングで潜在軌跡を生成**しエージェントが**包括的計画視点を維持**。**動的シナリオの計画レベル推論評価用ベンチ**も提供。
- **差分・新規性**: 既存のツール呼び出しは離散的・同期的だったが、本研究は**連続表現により誤差累積を理論的に低減**し、**未見ツールへの適応性を改善**。`HEAVYSKILL`([2605.02396](https://arxiv.org/abs/2605.02396)) と思想を共有する「**推論プロセス自体の再設計**」潮流。

### 13.4 Planning

#### [May 2026] "Planning in the LLM Era: Building for Reliability and Efficiency" [[paper](https://arxiv.org/abs/2605.21902)] 📖

- **概要**: 著者 Michael Katz, Harsha Kokel, Kavitha Srinivas, Shirin Sohrabi（IBM Research、classical planning界の著名研究者）。LLM時代のプランニング手法を整理。**単発プラン生成→LLM+制約付き外部探索のハイブリッド(非健全・非完全)を経て、現在はLLMで検証可能な記号ソルバを生成しinference時に効率実行する方向への移行**を分析。
- **差分・新規性**: 既存の Planning サーベイ（`Understanding the planning of LLM agents`(2402.02716)、`PlanGenLLMs`(2502.11221)）の流れを汲み、**信頼性と効率性**という運用視点を主軸に置く。**Classical Planning 専門家による視点**は、ニューラル一辺倒の議論に対する貴重なバランス。

## 15. 横断テーマ: 全エージェント研究を貫く共通課題

### 15.1 課題1: 長期運用での「腐敗」問題

- **メモリ腐敗**: `Useful Memories Become Faulty`([2605.12978](https://arxiv.org/abs/2605.12978))が **GPT-5.4でARC-AGI 54%失敗**を実証、`STALE`([2605.06527](https://arxiv.org/abs/2605.06527))が**最良モデルでも55.2%**しか陳腐化検出できないことを示した。
- **検索品質の劣化**: `LongSeeker`([2605.05191](https://arxiv.org/abs/2605.05191)) の5編集操作で対処。
- **スキルの陳腐化**: `Ratchet`([2605.22148](https://arxiv.org/abs/2605.22148)) の**結果駆動退役**で対処。

**横断的解法**: **TTL / Validity Window / Supersedes リレーション / 退役機構**を一級市民として扱う。

### 15.2 課題2: 評価の現実性ギャップ

- **静的ベンチでの成功 ≠ 実世界での成功**: `WildClawBench`([2605.10912](https://arxiv.org/abs/2605.10912))で Claude Opus 4.7 でも 62.2%、`From Controlled to the Wild`([2605.10834](https://arxiv.org/abs/2605.10834))が実環境ペンテスト評価を主題化。
- **ベンチ汚染**: `FrontierSmith`([2605.14445](https://arxiv.org/abs/2605.14445)) の合成データが学習を加速する反面、汚染源にもなる。

**横断的解法**: **Live Benchmark / Docker内CLIエージェント実行 / 連続評価**をデフォルトに。

### 15.3 課題3: 失敗帰属

- **マルチエージェント系で誰の失敗か特定できない**: `Beyond Individual Intelligence`([2605.14892](https://arxiv.org/abs/2605.14892)) サーベイがLIFEフレームワークで主題化。
- **スキルが原因かハーネスが原因か区別できない**: `Counterfactual Trace Auditing`([2605.11946](https://arxiv.org/abs/2605.11946)) が**合格率+0.3%でも522件の挙動変化**を検出。

**横断的解法**: **因果的トレース監査 / 構造化ログ / トレースID 伝播**。

### 15.4 課題4: 安全と性能のトレードオフ

- **スキルが攻撃ベクタにもなる**: `SkillScope`([2605.05868](https://arxiv.org/abs/2605.05868)) が**過剰権限を88.56%削減**しつつ正規タスク完了を維持。
- **ツール出力が信頼できない**: `Trust No Tool`([2605.17453](https://arxiv.org/abs/2605.17453)) の**VISTA-Guardで84.2%精度**。
- **行動評価では捉えられない**: `Position: Behavioural Assurance...`([2605.15164](https://arxiv.org/abs/2605.15164)) が**21ガバナンス文書分析**で構造的監査の必要性を提起。

**横断的解法**: **最小権限原則のスキル単位適用、ツール出力の検証ラッパー、メカニスティック解釈性への接続**。

### 15.5 課題5: 評価混在問題

- **メモリベンチがチャットに偏っている**: `MemGym`([2605.20833](https://arxiv.org/abs/2605.20833)) が**「メモリ独立スコア」**を導入。
- **既存ベンチが推論能力とメモリ能力を混在**: `EvoMemBench`([2605.18421](https://arxiv.org/abs/2605.18421)) が記憶スコープ×記憶内容の2軸で評価。

**横断的解法**: **能力ごとに評価を分離する設計**を benchmark 構築時に明示。

### 15.6 課題6: 探索量の逆効果

- `DataClawBench`([2605.02503](https://arxiv.org/abs/2605.02503))が**探索量増加が改善に必ずしも繋がらない**ことを発見。
- `Useful Memories Become Faulty`([2605.12978](https://arxiv.org/abs/2605.12978))も**更新が逆効果になる**ことを示した。

**横断的解法**: **「もっと → よくなる」の安易な仮定を捨て、`Ratchet` 系の hygiene 機構で**「不要な変更を抑制する」**設計に。

## 16. 共通の解法パターン7選

### パターン A: Hygiene Layer（衛生層）

進化・更新・統合の前後に**整合性チェック・冪等性・ロールバック**を強制する層を入れる。

- メモリ更新: `Ratchet`([2605.22148](https://arxiv.org/abs/2605.22148)) の**4機構**（結果駆動退役・アクティブキャップ・メタスキル指針・パターン正規化）
- 妥当性検証: `STALE`([2605.06527](https://arxiv.org/abs/2605.06527)) の **CUPMem**
- スキル承認: `SkillsVote`([2605.18401](https://arxiv.org/abs/2605.18401))

### パターン B: Adaptive Interface（適応的インターフェース）

モデルではなくインターフェース側を環境/タスクに適応させる。

- `Life-Harness`([2605.22166](https://arxiv.org/abs/2605.22166))が**1モデル→17モデル転送可能**で実証
- `Code as Agent Harness`([2605.18747](https://arxiv.org/abs/2605.18747)) の3層構造
- `Is Grep All You Need?`([2605.15184](https://arxiv.org/abs/2605.15184))の**grep > ベクタDB**の発見

### パターン C: Causal Trace（因果トレース）

実行トレースから因果関係を抽出し、失敗帰属・進化判断・監査に使う。

- `Counterfactual Trace Auditing`([2605.11946](https://arxiv.org/abs/2605.11946))が**合格率+0.3%でも522件の挙動変化検出**
- `HarnessAudit`([2605.14271](https://arxiv.org/abs/2605.14271)) の3軸（境界遵守・実行忠実性・システム安定性）

### パターン D: Lifecycle Governance（ライフサイクル統治）

生成・利用・廃棄を一貫して管理する。

- `SkillsVote`([2605.18401](https://arxiv.org/abs/2605.18401)) の収集→推薦→進化
- `CUGA`([2605.20874](https://arxiv.org/abs/2605.20874)) の5チェックポイント
- `SafeHarbor`([2605.05704](https://arxiv.org/abs/2605.05704)) の階層メモリガードレール

### パターン E: Capability Ladder（能力ラダー）

「できる/できない」を段階的に測る代わりに、難易度の階段で評価する。

- `ExploitBench`([2605.14153](https://arxiv.org/abs/2605.14153)) の**16段階**（カバレッジ→任意コード実行）
- `WildClawBench`([2605.10912](https://arxiv.org/abs/2605.10912)) の Claude Opus 4.7 が**62.2%**

### パターン F: Validity-aware Memory（有効性意識型メモリ）

記憶に妥当性ウィンドウ・条件付き有効性を埋め込む。

- `STALE`([2605.06527](https://arxiv.org/abs/2605.06527)) の **CUPMem**
- `Useful Memories Become Faulty`([2605.12978](https://arxiv.org/abs/2605.12978)) の**明示的ゲート統合**
- `TriMem`(Rethinking How to Remember, [2605.19952](https://arxiv.org/abs/2605.19952)) の**3表現併用**

### パターン G: Single-Step Compression（単一段階圧縮）

多段階の処理を、解釈可能で効率的な単一段階に圧縮する。

- `SIRA`([2605.06647](https://arxiv.org/abs/2605.06647)) が**多段階検索を単一語彙クエリに圧縮**
- `Compiling Agentic Workflows into LLM Weights`（NOT_FOUND）の方向性とも整合

## 17. 実装者向けTips集（保存版）

### 17.1 メモリシステム

1. **`Useful Memories Become Faulty`の警告**: 自動上書きは禁止、統合は**明示的にゲート**。**元証拠を上書きしない統合能力**が必須要件。
2. **`valid_until` を明示**: `STALE` の**Implicit Conflict**対策。全レコードに妥当性ウィンドウ付与。
3. **オフライン consolidation pass** (`Auto-Dreamer`[2605.20616](https://arxiv.org/abs/2605.20616)): GRPO 学習でメモリバンクを**1/12に縮小**しつつ性能 +7pt。
4. **3表現併用** (`TriMem`[2605.19952](https://arxiv.org/abs/2605.19952)): 生セグメント・原子事実・合成プロファイル。
5. **モジュラー化されたメモリモデル** (`MeMo`[2605.15156](https://arxiv.org/abs/2605.15156)): 別の小モデルとして扱う。

### 17.2 Skills

1. **トリガー条件と最小権限を仕様レベルで明示** (`SkillScope`[2605.05868](https://arxiv.org/abs/2605.05868)): 過剰権限88.56%削減。
2. **counterfactual トレース監査** (`Counterfactual Trace Auditing`[2605.11946](https://arxiv.org/abs/2605.11946)): 飽和タスクの隠れた挙動シフトを検出。
3. **生成パイプラインと評価ハーネスをセットで** (`SkillGenBench`[2605.18693](https://arxiv.org/abs/2605.18693))。
4. **退役機構を最初から組み込む** (`Ratchet`[2605.22148](https://arxiv.org/abs/2605.22148)): 8アブレーションで必須性検証。
5. **ライフサイクル統治** (`SkillsVote`[2605.18401](https://arxiv.org/abs/2605.18401)): Terminal-Bench 2.0 で**+7.9pp**。

### 17.3 マルチエージェント系

1. **オーケストレーション層をベイズ整合的に** (`Bayes-consistent orchestration`[2605.00742](https://arxiv.org/abs/2605.00742)): LLM内部ではなく外側でベイズ性担保。
2. **失敗帰属用のトレースID**を全メッセージに伝播（`Beyond Individual Intelligence`[2605.14892](https://arxiv.org/abs/2605.14892) LIFE フレームワーク）。
3. **状態管理は明示的に**: `STORM`([2605.20563](https://arxiv.org/abs/2605.20563)) が worktree分離より優れることを実証。
4. **再帰的最適化** (`Recursive Agent Optimization`[2605.06639](https://arxiv.org/abs/2605.06639)) で**コンテキスト窓を超えるタスク**を扱う。`Ratchet`系hygieneと併用。

### 17.4 安全性

1. **行動評価だけに依存しない** (`Position: Behavioural Assurance`[2605.15164](https://arxiv.org/abs/2605.15164)): 21ガバナンス文書分析を踏まえ、メカニスティック解釈性を併用。
2. **ハーネスレベルの監査** (`HarnessAudit`[2605.14271](https://arxiv.org/abs/2605.14271))の3軸を独立layer に。
3. **ツール出力を信頼しない** (`Trust No Tool`[2605.17453](https://arxiv.org/abs/2605.17453)): VISTA-Guard で 84.2%。
4. **設計時ガバナンス** (`CUGA`[2605.20874](https://arxiv.org/abs/2605.20874)) の5チェックポイント。
5. **可観測性は事前設計** (`Visibility into AI Agents`[2401.13138](https://arxiv.org/abs/2401.13138)) の3層（ID/ログ/通知）。

### 17.5 コーディングエージェント

1. **生成より保守を評価** (`To What Extent Does Agent-generated Code Require Maintenance?`[2605.06464](https://arxiv.org/abs/2605.06464))。
2. **修復は根本原因から** (`Kumushi`[2605.04251](https://arxiv.org/abs/2605.04251)): 178脆弱性で専用APR上回り。
3. **リポジトリ階層メモリ** (`MemRepair`[2605.17444](https://arxiv.org/abs/2605.17444)): SEC-Bench 58.0% SOTA。3要素（History-Fix/Security-Pattern/Refinement-Trajectory）。
4. **問題合成のスケーリング** (`FrontierSmith`[2605.14445](https://arxiv.org/abs/2605.14445)): ALE-bench +309 pt。

### 17.6 検索/Retrieval

1. **長期検索ではコンテキストを弾性的に** (`LongSeeker`[2605.05191](https://arxiv.org/abs/2605.05191)) の5編集操作（Skip/Compress/Rollback/Snippet/Delete）。
2. **多段階検索の単一段階圧縮** (`SIRA`[2605.06647](https://arxiv.org/abs/2605.06647))でコスト削減。
3. **エンタープライズコンテキストはガバナンス層分離** (`Beyond Text-to-SQL`[2605.21027](https://arxiv.org/abs/2605.21027) / `AgenticRAG`[2605.05538](https://arxiv.org/abs/2605.05538))。
4. **「単段階→エージェント的ツール利用」が最大の性能向上源** (`AgenticRAG` BRIGHT +21.8pp の知見)。

### 17.7 Harness/環境

1. **モデル変更の前にハーネス見直し** (`Life-Harness`[2605.22166](https://arxiv.org/abs/2605.22166)): 1モデル→17モデル転送可能。
2. **既存のシンプルなツールを再評価** (`Is Grep All You Need?`[2605.15184](https://arxiv.org/abs/2605.15184)): grep > ベクタDB の場合多数。
3. **ハーネスをコードとして管理** (`Code as Agent Harness`[2605.18747](https://arxiv.org/abs/2605.18747)) の3層構造。
4. **ハーネス安全性も独立に監査** (`HarnessAudit`[2605.14271](https://arxiv.org/abs/2605.14271)) の3軸。

### 17.8 学習

1. **ホライズン短縮による安定化** (`On Training LLMs for Long-Horizon`[2605.02572](https://arxiv.org/abs/2605.02572)): 短縮ホライズンで訓練→長尺に転送。
2. **行動ガイダンスによるコールドスタート不要RL** (`ActGuide-RL`[2605.12004](https://arxiv.org/abs/2605.12004)): Qwen3-4B GAIA +10.7pp。
3. **GFCR枠組み** (`Generate, Filter, Control, Replay`[2605.02913](https://arxiv.org/abs/2605.02913)): ロールアウト設計の体系的選択。

9. **Adapting the Interface の影響** ── `Life-Harness`([2605.22166](https://arxiv.org/abs/2605.22166)) の**1→17モデル転送**が実用パイプラインに影響するか。

## 19. まとめ：今期のメッセージ

> **「賢いモデル」から「賢く運用可能なシステム」へ。**

今期のエージェント研究は、明らかに次のフェーズに入った。コミュニティの関心は次のように移っている:

- **モデルの能力スコア** → **運用可能性・監査性・寿命**
- **新しい技法の提案** → **失敗パターンの体系化・批判的サーベイ**
- **個別タスクのSOTA** → **ライフサイクル全体の設計**

これは、エージェント研究が **「論文を書く研究」から「製品を作るための研究」** へ成熟しつつある証拠とも言える。

### 「根源的疑義の3部作」

特に次の3本は、今期のフラッグシップ論文として記憶すべき:

1. **`Position: Behavioural Assurance Cannot Verify the Safety Claims Governance Now Demands`** ([2605.15164](https://arxiv.org/abs/2605.15164))
   ── **評価**の根幹への疑義。**21ガバナンス文書分析**を踏まえ、行動評価では原理的に検証不能な性質があると主張。

2. **`Useful Memories Become Faulty When Continuously Updated by LLMs`** ([2605.12978](https://arxiv.org/abs/2605.12978))
   ── **メモリ**の根幹への疑義。**GPT-5.4 が以前解けた ARC-AGI 問題の 54% で失敗**することを実証。

3. **`Agentic AI Scientists Are Not Built For Autonomous Scientific Discovery`** ([2605.08956](https://arxiv.org/abs/2605.08956))
   ── **自律性**の幻想への疑義。**McNamara誤謬・暗黙知欠如・多様性低下・単一ターン偏重**の4障壁を整理。

これらは今後数ヶ月の研究議論を牽引する可能性が高い。

### 「成熟を示す4本のサーベイ」

同時に、次の4本のサーベイが同時期に出たことは、**各サブ分野が「整理を要する成熟段階」に達した**ことを示している:

1. **`A Comprehensive Survey on Agent Skills`** ([2605.07358](https://arxiv.org/abs/2605.07358)) ── Skillsの分類学
2. **`Beyond Individual Intelligence`** ([2605.14892](https://arxiv.org/abs/2605.14892)) ── Multi-Agent の LIFE フレームワーク
3. **`Generate, Filter, Control, Replay`** ([2605.02913](https://arxiv.org/abs/2605.02913)) ── LLM RL Rollout 戦略
4. **`Planning in the LLM Era`** ([2605.21902](https://arxiv.org/abs/2605.21902)) ── LLM時代のプランニング統合

### 「実装に効く3つの転換点」

実装側で記憶すべき具体的知見:

1. **「モデル変更の前にハーネス見直し」**: `Life-Harness`([2605.22166](https://arxiv.org/abs/2605.22166)) の**1モデル→17モデル転送**は、ハーネス側投資の合理性を示す決定的証拠。
2. **「grep > ベクタDB の場合多数」**: `Is Grep All You Need?`([2605.15184](https://arxiv.org/abs/2605.15184)) は業界の RAG ファースト常識を覆す可能性。
3. **「単段階エージェント検索 vs 多段階」**: `SIRA`([2605.06647](https://arxiv.org/abs/2605.06647)) の単一語彙クエリ圧縮で、Deep Research コストを大幅削減できる可能性。
