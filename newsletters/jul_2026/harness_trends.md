# ハーネス（Agent Harness）研究トレンド（2026年7月）

> 対象：[harness](../../architecture/harness.md) の 2026年7月論文（12本）。各論文の arXiv HTML 本文を読んでまとめた。

## 先月からの差分

ここでいう「ハーネス」とは、モデル本体（重み）は変えずに、その周りでツールの呼び出し方・手順・メモリ・失敗したときのやり直しを担う仕組みのことだ。6月は「モデルを固定したまま、この外側のハーネスを自動で改善する」という方向が主流になった。7月の新しさは、次の3点にある。

第一に、ハーネスの改善が**テスト時**に移った。あらかじめ学習しておくのではなく、評価を走らせている最中に、実行の記録だけを手がかりにハーネスを書き換える。しかも正解ラベルを使わない（TTHE・MemoHarness・Living-Harness）。

第二に、「その改善は特定のモデルでしか効かないのか、別のモデルにも移せるのか」という対立が表に出た。HarnessBank は「改善はモデルごとに違い、万能のハーネスは存在しない」と言い、Living-Harness と MemoHarness は逆に、別のモデルへ移しても効くと報告する。

第三に、そして最も重要なのが、**評価への反証**だ。計算量をそろえ、学習に使っていない別のタスクで比べると、ハーネスの自動改善は「ただ何度も試すだけ」の素朴な方法に一貫して勝てない——そう Rethinking Evaluation が指摘した。あわせて、「実運用に耐えるか」（どこを直せばよいか、失敗はモデルとハーネスのどちらの責任か、ハーネスを盗まれないか）という問いも前に出てきた。

> ※数値はモデルとデータの条件を添えて記す。1本の論文だけの結果は末尾に「要追試」としてまとめた。

## 論文紹介

### テスト時に、正解を見ずにハーネスを直す

3本が別々のやり方で、「追加の学習も正解ラベルも使わず、評価の最中にハーネスを適応させる」ことを実現した。

[TTHE: Test-Time Harness Evolution](https://arxiv.org/abs/2607.08124)
エージェントのハーネスは実行できるプログラムなので、走らせてみれば「途中でエラーが出ないか」「答えが一貫しているか」といった手がかりが得られる。TTHE はこの手がかりだけを使って、ハーネスの候補をいくつも並行して作って走らせ、良さそうなものを選んで次に引き継ぐ。正解は最後まで見ない。SQL 生成（BIRD の難問セット）で正答率が 12% から 50% へ、ソフトウェア修正（SWE-bench Verified）で 20% から 35% へ上がった。ただし著者は「ハーネスが正常に動いても、問われたこととは違う答えを返すことがある」と率直に認める。候補が一度も作られないまま終わるタスクが約15%あり、本当はもっと良い候補があるのに選び損ねる場面もある。良し悪しを見分ける役の精度が、次の課題だ。

![TTHE](../assets/2607.08124-tthe-method.png)
> 図（TTHE）：正解ラベルのない一群のタスクの中で、今のハーネスを起点に候補を枝分かれさせ、実行の手がかりだけで選んでいく。（[論文](https://arxiv.org/abs/2607.08124)）

[MemoHarness: Agent Harnesses That Learn from Experience](https://arxiv.org/abs/2607.14159)
ハーネスを6つの部品（コンテキストの組み立て方、ツールの使い方、メモリの持ち方など）に分け、過去の事例を「どこでどう失敗したか」の診断メモ付きで蓄えておく。新しい問題が来たら、似た事例を引いてその場に合うハーネスを組む——追加の学習も、その場のフィードバックも要らない。端末操作のベンチマークで市販のコーディング支援を上回り、費用も安い（1回あたり $6.89、比較対象は $10.28）。ただし評価に使ったタスクが18問と少なく、各部品の効き目を切り分ける検証は不十分だと自ら述べている。

[Living-Harness Is an Interactive-Agent Evolver](https://arxiv.org/abs/2607.26598)
対話タスク向け。過去のやり取りから「こういう状況ではこう対処し、こう直す」というメモと、状態の移り変わりを表す地図を育てる。おかしな更新をはじく関門を通して、安全に積み上げていく。対話の成功率が上がっただけでなく、育てたハーネスを別のモデルへ移すと、まったく解けなかったモデル（あるドメインで 0%）が 4割ほど解けるようになった。ただし「必ず良くなる」保証はなく、元に戻す仕組みや再テストは未整備だ。

![Living-Harness](../assets/2607.26598-livingharness-overview.png)
> 図（Living-Harness）：各回のやり取りと評価から手がかりを取り出し、メモと状態遷移の地図を更新する。ツールとベースのコンテキストは固定したまま。（[論文](https://arxiv.org/abs/2607.26598)）

### モデルと一緒に育てる／小型で大型に迫る

[Co-Harness: Co-Evolving Harnesses and Model Weights for LLM Agents](https://arxiv.org/abs/2607.22688)
ここまでは「モデルは固定」だったが、Co-Harness はモデルとハーネスを交互に育てる。まず失敗の記録からハーネスの欠陥を直し、次に、その良くなったハーネスが生む質の高い記録を使ってモデルを微調整する。この往復で少しずつ伸びていく（数学の問題で平均して二十数ポイントの改善）。ただし著者は「①ハーネスの改善が記録の質を上げ、②モデルがそれを取り込み、③強くなったモデルが新たな改善余地を開く、という3条件がそろうときだけ効果が積み上がる」と釘を刺す。モデルの実力が頭打ちなら止まる。

![Co-Harness](../assets/2607.22688-coharness-main.png)
> 図（Co-Harness）：失敗からハーネスを直すループと、良い記録でモデルを微調整するループの二重構造。（[論文](https://arxiv.org/abs/2607.22688)）

[Better Harnesses, Smaller Models](https://arxiv.org/abs/2607.08938)
「良いハーネスは、モデルの非力さをどこまで肩代わりできるか」を正面から測った。小型モデルの失敗を分析してハーネスを自動で調整すると、業務タスクで大型モデルの約9割の性能を、費用は数%で出せた。ただし万能ではなく、手順が毎回変わる多様なタスクほど効きにくい。「ハーネスは難しさを吸収できるが、モデルに欠けている中核の能力までは代われない」と結論する。

### その改善は本当に効いているのか

[Rethinking the Evaluation of Harness Evolution for Agents](https://arxiv.org/abs/2607.12227)
今月いちばんの冷や水。ハーネスの自動改善を、計算量をそろえたうえで、「ただ何度も答えを引き直す」「前の答えを少しずつ直す」といった素朴な方法と公平に比べた。しかも、改善に使ったのと同じ問題ではなく、学習に使っていない別の問題で汎化を測った。すると、素朴な方法のほうがハーネス改善を上回る場面すらあり、別の問題での伸びはごくわずかだった。「今のハーネス改善は、練習した問題に過剰に適合しているだけで、公平に比べれば単なる数打ちに負ける」。派手な改善の数字は、条件をそろえて読み直す必要がある、という警告だ。

### 実運用に耐えるか——どこを直すか、誰の責任か、盗まれないか

[Harness Handbook](https://arxiv.org/abs/2607.13285)
ハーネスを自動で直すには、まず「どこを直せばよいか」を突き止めなければならない。この研究は、コードを「どんな振る舞いをするか」の地図に変え、直すべき箇所へ案内する。結果、より少ない計算で、より良い改修ができた。「正しい直し方を思いつくことより、影響する箇所をすべて見つけるほうが難しい」という指摘は、実務経験者ほど頷けるだろう。

[From Prompts to Contracts](https://arxiv.org/abs/2607.08028)
企業導入の話。守るべき挙動を「お願い文（プロンプト）」に書くのをやめ、出典付きの根拠と検証の関門といった、版管理された部品に移す。すると、裏側のモデルを別製品に差し替えても、コード側の検査はすべて通った。関門を外すと違反が続出した一方、関門があれば利便性を損なわずに守れた。標語は明快で、「プロンプトはガードレールにならない」。

[Model or Harness? An Interaction-Centric Taxonomy for Localizing Agent Failures](https://arxiv.org/abs/2607.28802)
失敗したとき、悪いのはモデルかハーネスか。これを取り違えると、直す場所を間違える（モデルを再訓練すべきなのにハーネスをいじる、など）。この研究は 41 種類の失敗を「どの部品とどの部品の間で壊れたか」に整理し、責任の所在を割り当てる。AI による判定と人の判定はよく一致した。診断のための共通の言葉を与える提案だ。

![Model or Harness?](../assets/2607.28802-modelorharness-flowchart.png)
> 図（Model or Harness?）：失敗を「部品どうしのつながりのどこで起きたか」として捉え、責任の側を割り当てる。（[論文](https://arxiv.org/abs/2607.28802)）

[Agent Harness Distillation](https://arxiv.org/abs/2607.28147)
ハーネスが強力な資産なら、それは盗む対象にもなる。外から質問を投げて相手の実行の仕組みを推測し、真似た「影武者」を作ると、性能が大きく跳ねた。ハーネスは外から抜き取れる知的財産だ、という新しい弱点を示し、偽の説明をわざと返して守る方法も提案している。

## この号のまとめ
- **確かなこと**：モデルを固定したまま、テスト時に正解なしでハーネスを適応させるやり方は、複数のベンチマークで安定して効く。育てたハーネスを別のモデルへ移して効いた例もある（Living-Harness）。
- **今月の注意**：ただし、その効果は「計算量をそろえ、学習に使っていない別タスクで比べる」と、素朴な方法に負けることがある（Rethinking Evaluation）。良し悪しの採点を AI に任せると甘くなる（DataClawEval）。数値は必ず「どのモデル・どのデータで、何と比べたか」を確認して読む。
- **1本のみで要追試**：小型モデルが大型の約9割を数%の費用で（Better Harnesses、7業務の1研究）／ハーネスは外から盗める（Agent Harness Distillation、1研究）。

## 次に読みたくなる問い
- 良し悪しを見分ける役（判定・検証）の精度をどう上げるか——テスト時の適応に共通する弱点。
- 「計算量をそろえ、別タスクで、規則で採点する」公平な比べ方の定着。
- いつモデルを、いつハーネスを直すかの使い分け（Co-Harness の先）。
